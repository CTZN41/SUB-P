# 슛 후보 탐지 속도 점검 (2026-11-02)

## 확인한 실행 방식

`phase7_pipeline.analyze_video`는 기본 8fps를 목표로 프레임을 고른다. 현재 59.99fps 시험 영상은 7프레임 간격이므로 실제 약 8.57fps이며, 599초에서 약 5,134장을 분석한다. 건너뛰는 원본 프레임도 OpenCV `grab()`으로 순서대로 읽는다.

선택한 각 프레임에서 농구공·사람·림 학습 모델을 640 크기로 CPU 실행한다. 사람이 없거나 화면 높이의 25%보다 작으면 같은 프레임을 960 크기로 다시 검사한다. 사람이 있으면 별도 자세 모델도 640 크기로 CPU 실행한다. 한 장에서 모델을 최대 세 번 순차 호출한다. 현재 PC는 i7-12700과 Intel UHD 770이며 코드에는 CPU가 명시되어 있다.

탐지가 끝나면 공 비행, 팔을 올리는 자세, 림 접근 증거를 결합하고 후보를 합친다. 다음 단계에서 놓친 자세 힌트와 불확실한 후보 주변을 30fps로 재탐지하고 OpenAI 검토를 실행한다. 재탐지 때 `analyze_video`를 다시 호출하며 모델도 다시 로드한다.

`analysis_jobs`는 분석 프레임 8장마다 취소 여부를 DB에서 조회하고, 진행 콜백에서도 작업·분석 조회와 갱신 커밋을 수행한다. 약 10분 영상에서는 각 콜백이 640회가량 실행될 수 있다. Supabase 네트워크 대기가 분석 루프를 막을 수 있지만, DB 대기 시간은 아직 따로 측정하지 않았다.

## 측정 근거와 한계

- 기존 27초 분석 `ac12ab8d-a276-448f-af9d-7b9b9c4b19bd`: 분석 프레임 203장, 640 객체 탐지 203회, 960 재검사 없음. 후보 탐지 102.10초, 집중 재탐지·슛 확인 71.27초, 상세 AI 27.92초였다. 고해상도 재검사만 없애서 모든 지연이 해결되는 것은 아니다.
- 현재 10분 분석은 14:26경에도 후보 탐지 중이었다. 영상 약 130초를 처리하는 데 시작 이후 약 12분이 걸렸다. 중간 관측 속도를 전체 완료 시간으로 확정하지 않는다.
- 객체 탐지·자세·디코딩·DB별 시간이 없으므로 원인별 기여율과 개선 배수는 미측정이다. 진행 중인 시험에 부하를 더하지 않도록 별도 모델 벤치마크는 실행하지 않았다.

## 다음 개선 순서

1. 별도 짧은 영상 시험에 디코딩, 객체 640/960, 자세, DB 대기, 모델 초기화 시간을 각각 기록한다. 후보 시각과 구역 결과를 기존 기준과 함께 보존한다.
2. 프레임 수 기준 DB 조회·갱신을 실제 경과 시간 기준으로 제한하고 한 번의 상태 조회를 재사용한다. 취소 반영 지연과 서버 재시작 중단 감지는 회귀 시험한다. 탐지 모델·프레임 입력을 바꾸지 않는 첫 개선으로 적합하다.
3. 학습된 객체 모델과 자세 모델을 OpenVINO 실행 형식으로 변환해 Intel CPU에서 비교한다. 원본 모델은 보존한다. FP32부터 확인하고 INT8은 별도 정확도 시험 뒤 판단한다. Intel 내장 GPU 경로는 설치·장치 지원 확인 후 별도로 시험한다.
4. 멀리 있는 선수 때문에 매번 640→960을 반복하는 구간을 측정한다. 구간별 입력 크기를 선택하거나 신뢰도가 떨어진 때만 960 재검사하는 방식, 적은 수의 프레임 배치 처리, 재탐지 시 모델 재사용을 비교한다.
5. 그래도 부족하면 낮은 빈도의 전체 탐지와 슛 동작 주변의 촘촘한 분석을 결합한다. 과거 4fps에서 누락이 있었으므로 전 구간 fps를 단순히 낮추지 않는다. 자세 모델을 생략하거나 부분 화면만 읽는 방식도 놓치는 슛이 없는지 별도 검증 후 적용한다.

각 변경은 같은 고정 구간에서 기존 방식과 각각 실행하고 시간, 후보 누락·오탐, 릴리스 시각, 위치 변화와 취소 반응을 비교한다. 실행 중인 10분 작업에는 변경을 적용하지 않았다. OpenAI 토큰 감소는 이 로컬 속도 개선에서 보장하지 않는다.

공식 참고: [OpenVINO 내보내기 및 지원 작업](https://docs.ultralytics.com/integrations/openvino), [프레임 배치 추론](https://docs.ultralytics.com/modes/predict). 문서의 속도 사례는 이 PC에서의 측정 결과가 아니다.

## 개선과 실제 비교 결과

사용자가 10분 전체 분석을 취소한 뒤 같은 시험 파일의 앞 180초만 별도 실행했다. 학습된 v4·자세 가중치, 약 8.57fps 간격과 후보 규칙을 유지하고 실행 형식만 비교했다. OpenVINO는 정밀도를 낮추지 않은 FP32 변환이다. 아래 시간은 DB 콜백과 AI를 제외한 로컬 후보 탐지이며 각 방식 한 번씩 순차 실행했다. 모델 준비·첫 추론 시간을 포함한다.

| --- | ---: | ---: | --- |

이 PC에서는 OpenVINO CPU가 가장 빨랐으며 기존보다 처리 시간이 **50.68% 감소**했다. 후보 수 27개가 실제 슛 정답 27개라는 뜻은 아니다. 이 3분 구간의 독립 정답표는 새로 만들지 않았다.

선택한 OpenVINO CPU를 서로 다른 짧은 영상으로 다시 비교했다. 아래 시간은 누락 힌트 재검사를 포함하지만 이번 여섯 영상에서는 추가 재검사 구간이 없었다.

짧은 영상 합계 시간은 **48.56% 감소**했고 이전에 확인한 후보 수·시각을 유지했다. 이는 이번 표본의 기존 결과 보존을 확인한 것이며 전체 영상의 정확도 100% 또는 90%를 입증한 것은 아니다. 원시 요약은 `backend/evaluation/results/candidate-speed-2026-11-02.json`에 저장했다. **이번 속도 비교의 OpenAI 호출·입력·출력 토큰은 모두 0**이다. 성공·실패·슛 종류·구역 판정은 실행하지 않았다.

프로그램에는 `CANDIDATE_RUNTIME` 선택과 재탐지 단계의 동일 실행 장치 전달을 반영했다. 현재 PC의 `.env`는 `openvino_cpu`를 선택한다. 원본 `.pt` 가중치는 보존하고 `backend/models/*_openvino_model`에 변환 모델을 보관한다. 새 PC에서는 `requirements-openvino.txt` 설치와 변환 스크립트 실행이 필요하다. 예시 설정은 기본 `torch`를 제공한다.

진행 상태의 DB 조회는 실제 시간 2초 간격, 저장은 5초 간격으로 제한하고 최근 저장 시 확인한 취소 상태를 재사용한다. 실제 취소 반영은 다음 검사·프레임 처리·DB 응답 시간의 영향을 받는다. 모델 검사 프레임은 줄이지 않았다. DB 작업 횟수·대기 시간과 모델·디코딩 단계 시간을 새 결과에 남긴다. DB 변경 자체의 Supabase 실작업 전후 시간은 아직 비교하지 않았으므로 위 속도 감소에 포함해 주장하지 않는다.

프론트에는 경과·완료 시간과 후보 탐지 소요 시간을 추가하고 전체 분석 버튼에 유료 AI 포함을 표시했다. 후보만 시험하는 이번 실행은 별도 로컬 명령으로 수행했다. 백엔드 144개 시험과 프론트 빌드가 통과했다. 린트에는 기존 `ShotReviewPage`의 effect 관련 경고 4개가 남아 있으며 이번 진행 화면의 새 경고는 없다. 두 서버 재실행 후 8000 health와 5173 홈은 HTTP 200이었다.
