# ShotMap AI 상세 설계 문서(SDD)

## 1. 문서 목적

이 문서는 `mvp.md`, `PRD.md`, `spec.md`, `plan.md`를 실제 프로그램 구조로 옮기기 위한 Phase 0 설계 문서입니다.

화면, 로컬 API, 영상 분석, OpenAI 보조 판단, 데이터 저장과 파일 보관의 역할을 구분합니다. 구현 중 세부 라이브러리가 바뀌더라도 사용자의 행동과 저장 결과는 이 문서의 기준을 유지합니다.

## 2. Phase 0에서 확정한 범위

- 첫 버전은 현재 Windows PC에서 한 명이 사용하는 로컬 프로그램입니다.
- 회원가입, 로그인과 인터넷 배포는 만들지 않습니다.
- 개인 연습 영상 분석은 필수입니다.
- 3대3은 최대 6명의 등록, 화면 지정, 슈터 수정과 선수별 결과 흐름을 구현합니다.
- 공식 정확도 합격 여부는 개인 연습 영상으로 판단합니다.
- 입력은 MP4 한 개, 최대 10분, 최대 5GB입니다.
- OpenAI는 전체 원본이 아니라 슛 후보의 필요한 장면만 확인합니다.
- 자동 분석이 애매하면 `확인 필요`로 남기고 사용자가 수정합니다.
- 원본 영상과 결과는 사용자가 직접 삭제하기 전까지 현재 PC에 보관합니다.

2026-11-03 후속 결정: 위 내용은 로컬 첫 버전의 범위다. 향후 웹 배포는 Cloudflare 중심으로 준비하고 영상은 R2, 분석 기록은 기존 Supabase PostgreSQL을 사용하는 방향으로 정했다. 현재 실제 배포는 하지 않았으며 FastAPI·영상 분석 서버의 실행처는 미정이다. 저장·재생 구조와 배포 순서는 `plan.md`의 「2026-11-03 향후 배포 방향 결정: Cloudflare 중심」을 따른다.

### 환경 결정

- 분석은 CPU에서도 동작하는 구조로 먼저 만듭니다.
- GPU 전용 기능은 필수 조건으로 두지 않습니다.
- 영상 프레임은 순서대로 읽고 사용이 끝난 프레임은 바로 해제합니다.
- 동시에 여러 영상을 분석하지 않고 첫 버전에서는 한 작업만 실행합니다.
- Python 3.13에서 필요한 영상 AI 패키지가 동작하지 않으면 Python 3.12 가상환경을 사용합니다. 실제 설치 전 공식 지원 범위를 다시 확인합니다.
- FFmpeg는 영상 정보 확인과 후보 장면 생성에 필요하므로 Phase 1~3 사이에 설치합니다.

## 4. 확정 기술 구성

### 4.1 화면

- React
- TypeScript
- Vite
- 일반 CSS 또는 화면별 CSS Module
- 3D 표현은 React Three Fiber 기반

화면은 사용자 입력, 진행 상태, 결과 확인과 수정만 담당합니다. 무거운 영상 분석을 브라우저에서 직접 실행하지 않습니다.

### 4.2 로컬 API와 작업 제어

- FastAPI
- Python
- 요청과 응답 데이터 검사는 Pydantic
- 데이터 저장은 SQLAlchemy와 Supabase PostgreSQL을 사용합니다. 기존 SQLite 파일은 삭제하지 않고 시험·과거 자료로만 보존합니다.
- 데이터 구조 변경은 Alembic

FastAPI는 파일 등록, 데이터 조회·수정, 분석 시작·취소와 결과 제공을 담당합니다.

### 4.3 영상 처리

- FFmpeg 또는 ffprobe: 영상 길이, 해상도, fps, 코덱 확인과 후보 장면 생성
- OpenCV: 프레임 읽기, 좌표 변환과 영상 처리
- 선수·공·골대 탐지는 교체 가능한 분석 모듈로 분리
- 구체적인 탐지 모델은 Phase 7의 속도·정확도 시험 후 확정

특정 모델에 프로그램 전체가 묶이지 않도록 `선수 찾기`, `공 찾기`, `골대 찾기`, `슛 후보 찾기` 기능을 각각 교체 가능한 형태로 만듭니다.

### 4.4 OpenAI

- 서버의 환경설정 파일에서 API 키를 읽습니다.
- 전체 영상을 전송하지 않습니다.
- 슛 후보에서 필요한 프레임 또는 짧은 장면만 사용합니다.
- 주 역할은 슛 종류 판단과 로컬 분석이 애매한 장면의 보조 검토입니다.
- 기본 모델은 `gpt-6.1-terra`, 보조 재검토 모델은 `gpt-6.1-sol`이며 환경설정에서 바꿀 수 있습니다.

### 4.5 저장

- Supabase PostgreSQL(현재 실행): 분석, 선수, 슛, 코트 기준점, 작업 상태와 오류 기록
- SQLite(보존): 전환 전에 사용한 파일은 삭제하지 않으며 운영 실행에서 자동으로 사용하지 않습니다.
- 로컬 파일: 원본 영상, 후보 장면과 필요한 임시 결과
- 통계는 슛 기록에서 다시 계산할 수 있도록 설계

## 8. 분석 상태 변화

```text
등록 중
  ├─ 등록 실패 → 기록 생성 안 함 또는 안전하게 정리
  └─ 등록 완료 → 설정 필요

설정 필요
  ├─ 코트·선수 설정 계속
  ├─ 삭제
  └─ 분석 시작 → 대기 중

대기 중
  ├─ 작업 시작 → 분석 중
  └─ 취소 → 취소됨

분석 중
  ├─ 확인할 기록 있음 → 검토 필요
  ├─ 확인할 기록 없음 → 완료
  ├─ 사용자가 취소 → 취소됨
  └─ 처리 오류 → 실패

검토 필요
  ├─ 확인 필요 기록이 남음 → 검토 필요
  └─ 모두 확인·수정 → 완료

실패 또는 취소됨
  ├─ 다시 분석 → 대기 중
  └─ 삭제

완료
  ├─ 결과 조회·수정
  ├─ 수정 후에도 완료 유지
  └─ 삭제
```

### 비정상 종료 복구

- `분석 중` 작업은 일정 시간마다 `heartbeat_at`을 갱신합니다.
- 프로그램 시작 시 오래된 `분석 중` 작업을 찾습니다.
- 실제 작업이 없으면 계속 진행 중이라고 표시하지 않고 `중단됨` 안내가 포함된 실패 상태로 바꿉니다.
- 다시 분석할 때 기존 미완성 슛과 임시 파일을 먼저 정리합니다.

## 9. 코트 좌표 규칙

- 가상 코트는 골대가 있는 베이스라인 중앙을 기준으로 방향을 통일합니다.
- `x`는 코트의 왼쪽에서 오른쪽 방향입니다.
- `y`는 골대가 있는 베이스라인에서 하프라인 방향입니다.
- 저장 좌표는 실제 코트 단위를 기준으로 하되 화면 크기와 분리합니다.
- 영상 좌우가 뒤집혀도 보정 결과가 같은 가상 코트 방향을 사용해야 합니다.
- 코트 밖 좌표는 저장하지 않습니다.
- 구역 경계 좌표는 미리 정한 우선순위로 한 구역에만 배정합니다.

14개 구역의 정확한 좌표 경계와 우선순위는 Phase 2에서 단위 테스트와 함께 고정합니다.

## 10. 로컬 API 역할

구체적인 주소 이름은 구현 시 바뀔 수 있지만 다음 동작은 분리합니다.

| 영역 | 필요한 동작 |
|---|---|
| 분석 등록 | 영상과 기본 정보 등록, 검사 결과 반환 |
| 분석 조회 | 목록, 한 건 상세와 상태 조회 |
| 코트 보정 | 기준 장면 조회, 기준점 저장과 재설정 |
| 선수 | 등록, 수정, 화면 지정 정보 저장 |
| 작업 | 분석 시작, 진행 조회, 취소, 다시 시도 |
| 슛 | 목록, 한 건 조회, 추가, 수정, 삭제, 확인 |
| 결과 | 요약 통계, 14개 구역, 필터 결과 |
| 영상 | 원본 재생과 지정 시퀀스 재생 |
| 삭제 | 원본과 연결 결과의 동시 삭제 |

### 공통 응답 원칙

- 성공하지 않은 요청을 성공처럼 표시하지 않습니다.
- 사용자용 메시지와 내부 오류 코드를 구분합니다.
- 파일 경로와 API 키 같은 내부 비밀정보를 응답에 넣지 않습니다.
- 수정 요청은 같은 요청이 반복되어도 데이터가 중복되지 않도록 설계합니다.

## 11. 분석 작업 흐름

1. 원본 파일과 코트·선수 설정을 검사합니다.
2. 영상 정보를 다시 확인합니다.
3. 코트와 골대 기준을 불러옵니다.
4. 프레임을 순서대로 읽습니다.
5. 선수, 공과 골대를 추적합니다.
6. 슛 후보를 찾고 중복 후보를 합칩니다.
7. 후보 순간의 선수 발 위치를 코트 좌표로 바꿉니다.
8. 공과 림 주변 움직임으로 성공·실패를 판단합니다.
9. 슛 후보의 필요한 장면만 OpenAI 보조 분석에 사용합니다.
10. 슛 종류와 시퀀스 범위를 저장합니다.
11. 불확실한 항목과 이유를 `확인 필요`로 표시합니다.
12. 모든 슛에서 통계를 다시 계산합니다.
13. 확인 필요 기록이 있으면 `검토 필요`, 없으면 `완료`로 바꿉니다.

각 단계 사이에서 취소 요청을 확인합니다. 취소되면 원본과 설정은 유지하고 미완성 결과만 정리합니다.

## 12. OpenAI 입력과 출력 계약

### 입력 원칙

- 분석 번호 대신 외부 전송에 불필요한 내부 정보는 제거합니다.
- 선수 이름이 필요하지 않으면 `player_1`처럼 익명 표시를 사용합니다.
- 후보마다 후보 시점 5초 전부터 5.5초 후까지 전체 장면 17장과 선수 주변 확대 장면 최대 6장만 사용합니다.
- 릴리스 전후 장면은 0.3~0.7초 간격으로 촘촘하게 배치하고, 나머지는 약 1초 간격으로 넓게 확인합니다.
- 판단 대상과 가능한 슛 종류를 명확히 전달합니다.
- 원본 파일 경로, API 키와 다른 분석 정보는 전송하지 않습니다.

### 기대 출력 형태

```json
{
  "is_shot": true,
  "is_shot_confidence": 0.93,
  "outcome": "made",
  "outcome_confidence": 0.84,
  "shot_type": "dribble_pull_up",
  "shot_type_confidence": 0.88,
  "sequence_start_offset_ms": -2200,
  "sequence_end_offset_ms": 1800,
  "confidence": 0.82,
  "review_required": false,
  "visible_evidence": ["release", "ball_rising", "rim_passage"],
  "reason": "공이 림을 통과하는 장면이 보임"
}
```

### 모델 재검토와 항목별 합의

- Terra가 슛 시도, 종류와 성공 여부를 각각 판단합니다.
- 어느 한 항목이 불확실하거나 결과가 `unclear`, 종류가 `needs_review`이면 Sol이 같은 장면을 한 번 더 검토합니다.
- 두 모델이 같은 판단을 내린 항목은 자동 확정합니다.
- 슛과 종류는 같지만 성공 여부가 다르면 슛과 종류는 저장하고 성공 여부만 `unclear`로 둡니다.
- 림 통과가 직접 보이지 않을 때만 화면에 실제로 보이는 공의 낙하, 리바운드 행동과 점수 표시 변화를 보조 근거로 사용합니다.
- 근거가 없는 화면 밖 결과는 추측하지 않습니다.

### 허용 슛 종류 값

- `catch_and_shoot`
- `set_shot`
- `dribble_pull_up`
- `layup`
- `dunk`
- `fadeaway`
- `step_back`
- `turnaround`
- `hook_shot`
- `other`
- `needs_review`

`layup`과 `dunk`는 별도 값입니다. 움직이면서 공을 림 옆에서 위로 놓는 장면은 `layup`, 공을 쥐고 림 높이에서 아래로 밀어 넣는 장면은 `dunk`로 구분합니다. 판정 근거가 부족하면 `needs_review`로 둡니다.

### 응답 검사

- 정의하지 않은 값은 그대로 저장하지 않습니다.
- 슛 시도, 성공 여부와 슛 종류의 신뢰도를 각각 검사합니다.
- 시작과 끝이 영상 범위를 벗어나면 실제 범위로 줄입니다.
- 시작이 끝보다 늦으면 기본 구간을 사용하고 확인 필요로 표시합니다.
- 응답을 읽지 못하면 로컬 분석 결과를 유지하고 슛 종류를 확인 필요로 둡니다.
- API 오류 원문을 그대로 사용자에게 보여주지 않습니다.

## 14. 파일 보관과 삭제

### 등록

- 사용자가 선택한 파일 이름을 그대로 내부 경로로 사용하지 않습니다.
- 분석 고유 번호와 안전한 내부 파일 이름을 사용합니다.
- 원본 확장자와 실제 형식이 MP4인지 모두 확인합니다.
- 업로드 원본은 `original.mp4`로 보존합니다.
- H.264가 아닌 MP4는 FFmpeg로 같은 fps의 `playback.mp4`를 만들고 브라우저 재생에만 사용합니다.
- 호환 사본은 H.264 영상, AAC 음성, `yuv420p` 픽셀 형식과 빠른 재생 시작 옵션을 사용합니다.
- 복사가 완료된 뒤에만 등록 성공 상태로 바꿉니다.

### 임시 파일

- 분석별 작업 폴더를 사용합니다.
- 작업 성공 후 다시 만들 수 있는 임시 프레임은 정리합니다.
- 재생과 검토에 필요한 후보 장면은 보존 여부를 별도로 정합니다.

### 삭제

1. 삭제 대상을 데이터에서 확인합니다.
2. 작업 중이면 먼저 취소하고 종료를 확인합니다.
3. 원본과 임시 파일을 삭제합니다.
4. 연결된 슛, 선수, 코트와 작업 정보를 삭제합니다.
5. 일부 실패 시 남은 항목을 기록하고 완료로 표시하지 않습니다.

첫 버전은 삭제 복구를 보장하지 않습니다.

## 16. 성능 설계

- 첫 버전은 동시에 한 분석만 실행합니다.
- 프레임을 한 장씩 또는 작은 묶음으로 처리합니다.
- 미리보기용 크기와 최종 판정용 크기를 구분할 수 있게 합니다.
- 모든 단계에서 원본 시간 정보를 유지합니다.
- 선수·공 탐지 결과는 필요한 범위에서 재사용하여 같은 프레임을 반복 분석하지 않습니다.
- OpenAI는 슛 후보에만 호출하고 같은 후보의 성공한 응답을 다시 호출하지 않습니다.
- 작업 진행 상태는 처리한 영상 시간으로 표시합니다.
- 여유 메모리가 부족하면 분석 시작 전에 경고할 수 있게 준비합니다.

현재 예상 시간인 1분 2~5분, 10분 15~40분은 아직 측정값이 아닙니다. Phase 7과 Phase 14에서 실제 값으로 교체합니다.

2. `index.css`·`App.css`의 공통 색상·간격·글자·카드·버튼 값을 먼저 정리한다. 화면별 중복 색상을 공통 변수로 묶는다.
3. 메뉴 → 등록/설정/진행 → 영상별/월별 기록 → 결과·편집 순으로 적용한다. 현재 DOM의 의미·화면 배치와 이벤트 연결을 보존하고 CSS 변경을 우선한다.
4. 3D 컨테이너 등 자체 CSS를 쓰는 영역의 바깥 카드만 맞춘다. Three.js의 카메라·좌표 변환·구역 모양·선택 코드는 변경 대상에서 제외한다.
5. PC 1920×1080·1440×900·1280×720에서 긴 제목·카드 정렬·스크롤·선택 강조·텍스트 대비와 잘림을 확인한다. 기존 좁은 화면 대응을 깨뜨리지 않는다.
6. 기존 기록으로 요약 필터·2D→3D 연결·번호 선택·반복 재생·토글·저장 후 재진입·월별 원본 이동·삭제 취소를 확인한다. 실제 삭제·수정 검증은 전용 시험 기록으로 구분한다. 디자인 검증을 위해 새 유료 영상 분석을 실행할 필요는 없다.
7. 프론트 자동시험·빌드·린트를 확인하고 API 주소·요청 내용·DB 집계·기록 수가 디자인 변경으로 달라지지 않았는지 확인한다. 이후 실제 화면 검증 결과와 사용자의 피드백을 반영한다.

## 23. 영상별 선택 삭제와 전체 화면 가독성 (2026-11-03)

- 영상별 기록에 개별 체크박스·전체 선택·선택 해제·선택 삭제를 제공한다. 홈의 최근 기록에는 다중 선택을 표시하지 않는다.
- 삭제 요청 전 선택한 개수·제목·원본 파일명·삭제 범위를 대화상자에서 보여준다. 취소를 기본 포커스로 두고 취소나 Esc는 삭제 요청을 보내지 않는다.
- 확정하면 기존 단건 삭제 API로 선택한 ID를 한 번씩 순서대로 처리한다. 별도 서버 일괄 삭제 기능은 추가하지 않는다. 분석 중 삭제 방지 등 기존 서버 규칙을 그대로 사용한다.
- 성공한 기록은 즉시 목록·선택에서 제거한다. 실패한 기록은 남겨 오류를 표시하고 해당 기록만 재시도한다. 처리 중 중복 제출·선택 변경·대화상자 닫기를 막는다.
- 긴 동의 안내는 두 줄로, 미지정 기준점은 점별 목록으로, 삭제 범위와 복구 불가 문구는 별도 줄로 구분한다. 제목·파일명·선택 정보·오류는 영역에 맞춰 줄바꿈한다.
- 좁은 화면에서 버튼을 글자별로 찢지 않고 버튼 행을 다음 줄로 넘긴다. 코트 조작·영상 프레임 조작·편집 패널 제목도 같은 방식으로 정리한다.
- 기존 기록·새 영상 분석은 이 UI 검증을 위해 생성하거나 삭제하지 않는다. 실제 API와 차단된 전용 시험 화면 및 자동시험으로 선택 삭제를 확인한다.
