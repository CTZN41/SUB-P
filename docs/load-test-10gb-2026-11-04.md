# 1시간·10GB MP4 등록 부하 시험 — 2026-11-04

사용자가 제시한 아이폰 1080p/60fps·1시간 약10GB 조건에 맞춰, **전송·저장·구간 읽기**를 시험했다. 시험용 제한을 확대한 별도 서버에서 등록은 성공했다. 운영 화면은 여전히40분·5GiB 제한이며, 이 결과를 아이폰 원본이나1시간 전체 AI 분석의 통과로 해석하지 않는다.

## 환경과 시험 파일

- 기존8000/5173 서버와 실행 중33분 분석은 중단·재시작·수정하지 않았다. 같은 PC의 CPU/디스크를 공유하므로 하드웨어 경합까지 없다고 보장하지 않는다.
- 별도127.0.0.1:8011 서버와 시험용 SQLite·업로드·임시 폴더만 사용했다. 실제 등록·조회·영상 반환 라우트를 재사용했다. 분석 시작 라우트는 노출하지 않았고 OpenAI 키와 AI 사용을 비활성화했다. 운영 인증이나 DB 설정은 변경하지 않았다.
- `Downloads/10m 30S P.mp4`를 재인코딩 없이6회 이어 붙였다. 재생시간3600.016초,1920×1080,약59.998fps,215,994프레임이다.
- MP4 영상·오디오·인덱스는6,594,567,103바이트이며, 정상 MP4의 `free` 영역3,405,432,897바이트를 실제 쓰기로 추가했다. 총 **10,000,000,000바이트(10GB,약9.31GiB)**다. 빈 공간만 예약한 sparse 파일은 아니다.
- 따라서10GB 파일을 실제 전송·복사하는 부하는 재현하지만,10GB 전부가 압축 영상인 아이폰 HEVC의 디코딩·HDR·가변 프레임률 부하는 재현하지 않는다. 반복 영상의 인식 정확도 평가에도 사용하지 않았다.

## 저장과 읽기 검증

- 등록된10GB 전체를 SHA-256으로 다시 읽어 시험 원본과 일치했다: `4799b43eb9701f5fe9a20bd8a57905a2f6a2cfffca14084f5b19a79cac13d89e`.
- HTTP Range로0,5,000,000,000,9,999,934,464바이트부터 각각64KiB를 요청했다. 모두206·정확한 Content-Range와 바이트 일치를 확인했다. 응답은 각각약6.6/2.6/2.2ms다. 끝 바이트 검증은 MP4 여분 영역의 전송도 포함한다.
- 저장된 파일의00:00·15:00·30:00·45:00·59:58에서 각각30프레임,총150프레임을1920×1080으로 읽었다. 시점 이동과30프레임 읽기는 각각0.166/0.276/0.405/0.447/0.357초였다. 전체215,994프레임의 연속 디코딩은 수행하지 않았다.
- 시험 DB는 거절 조건0건,확대 조건1건의 등록만 있다. 두 DB 모두 분석 작업0건·슛0건이다. 유료 AI 호출0회다.
- 종료 뒤 시험용8011 포트가 닫히고 기존8000/5173이 모두200으로 응답했다. 임시 파일은 모두 정리됐다. 생성한 시험 원본과 성공 저장본은 합계약20GB로 별도 `backend/work/large-upload-2026-11-04`에 보관했다. 사용자의 Downloads 원본은 변경하지 않았다.

## 발견한 병목과 다음 순서

1. **용량 제한을 늦게 확인한다.** 현재 multipart 파서는10GB 전체를 임시 디스크에 받은 뒤 등록 함수의5GiB 검사를 수행한다. 파일 제한을 유지하더라도 전송 단계에서 총 요청/파일 크기를 제한해야 한다. multipart 부가 데이터와 청크 전송도 고려해야 하므로 Content-Length 하나만 믿는 방식은 피한다.
2. **10GB 등록 중 임시·최종 파일이 겹친다.** 사용자 원본을 제외해도 약20GB의 동시 저장 공간이 필요하다. 업로드 크기만 허용하기 전에 직접 스트리밍 또는 안전한 임시 파일 인계·중단 복구 설계를 검증한다. 배포 시에는 스토리지 직접 업로드·이어 올리기도 후속이다.
3. **아이폰 원본 호환성을 별도로 확인한다.** 실제 MOV/HEVC·HDR·가변fps 파일로 원본 읽기, 구간 탐색, 브라우저 호환 변환의 시간·추가 저장 공간을 측정한다. 이번 H.264 결과로1시간 변환 비용을 추정하지 않는다.
4. **1시간 YOLO/AI 전체 분석은 별도다.** 이번에는 전송·저장·표본 읽기만 검증했다. 인식 정확도·총 분석시간·토큰 비용·Chrome 직접 업로드/재생은 미검증이다. 운영40분·5GiB를 확대하는 제품 변경도 후속 결정이다.

## 중복 저장 개선 설계

2026-11-04 사용자가 실측을 바탕으로 개선 방향 설정을 요청했다. 아래는 구현할 설계와 합격 기준이다.

### 원인 확인과 Windows 추가 시험

설치된 Starlette1.10.0의 multipart 파서는 파일을 `SpooledTemporaryFile`에 받는다. 메모리 임계값은1MiB여서 대용량 파일은 임시 디스크로 넘어간다. 프론트의 FormData POST가 이 경로를 사용하며, 등록 서비스의 `save_upload()`가1MiB씩 다시 읽어 `original.mp4`에 기록한다. 전체 수신 뒤 두 번째 읽기·쓰기가 발생하는 구조다.

별도 시험 서버를 종료한 상태에서, 앞서 저장한 시험용10GB 파일을 같은 폴더의 `.part` 이름으로 바꾸고 원래 이름으로 되돌렸다. 이름 변경은0.614ms, 복원은0.444ms였다. 파일 ID와 크기가 유지됐고 앞·중간·끝 바이트가 같았다. Windows에서 명시적인 파일 경로를 관리하고 열린 핸들을 닫으면 같은 볼륨의 이름 변경을 사용할 수 있음을 확인했다. 이1회 시험의 rename 시간만으로 업로드 전체 성능을 확정하지 않는다.

### 1순위 수신 중 제한 적용

- 파일 전송 전에 이름·날짜·파일 크기·등록 정보를 작은 요청으로 확인하고, 현재 사용자에게 속한 업로드ID를 발급한다.
- 알 수 있는 파일 크기와 가용 디스크 공간을 먼저 확인한다. 전송 중에도 실제 누적 바이트를 제한해 헤더가 없거나 선언한 크기와 다른 경우를 처리한다.
- 기존 multipart 등록 경로에도 수신 단계의 요청 크기 상한을 둔다. multipart 부가 영역의 상한과 실제 파일 제한은 구분한다.
- 크기 초과는 수신 시점에413으로 종료하고 해당 업로드의 부분 파일을 정리한다. 현재69.81초처럼10GB 전체 수신 뒤 거절하는 대기를 줄이는 목표다.

### 2순위 `.part` 하나에 직접 기록하고 파일 확정

- 새 파일 전송 경로는 요청 스트림을 작은 청크로 받아 `uploads/.incoming/{upload_id}/original.part`에 직접 기록한다. 디스크 쓰기는 작업 스레드로 보내 진행 조회와 영상 재생의 응답성을 확보한다.
- `.incoming`과 최종 업로드 경로를 같은 저장 볼륨에 둔다. 파일 핸들을 닫고 MP4 형식·실제 크기·영상 메타데이터를 검증한 뒤 이름 변경으로 최종 경로에 확정한다. `.part`는 등록 목록이나 영상 반환 경로에서 공개하지 않는다.
- 등록 메타데이터·선수 생성 등 기존 로직은 수신 완료 파일을 받아 재사용하도록 분리한다. 프론트는 사전 정보 확인→파일 전송→등록 완료 흐름을 사용한다. 정상 등록 뒤 코트 설정으로 이어지는 화면 흐름을 검증한다.
- 현재 프레임워크 임시 파일의 내부 핸들을 직접 이동하는 방식은 Windows의 삭제 시점·열린 핸들 제약과 연결된다. 애플리케이션이 소유한 경로와 수명을 관리하는 수신 흐름을 구현한다.

### 3순위 실패·재시도 시 상태 일관성

- 전송 중단·공간 부족·잘못된 영상이면 해당 업로드의 실패 상태와 정리 결과를 기록한다. 서버가 재시작되면 활성 업로드와 만료된 부분 파일을 구별해 복구한다.
- 완료 요청을 재시도하면 동일 업로드ID의 등록 결과를 반환해 분석 기록 중복을 막는다. 같은 업로드ID의 동시 완료도 한 번만 확정한다.
- 현재 `register_video()`는 DB 커밋 뒤 `refresh()`가 실패해도 폴더 삭제 예외 분기로 들어간다. 개선 시에는 커밋 전 실패·커밋 성공·성공 여부 확인 대기를 구분한다. DB가 이미 확정됐을 가능성이 있는 파일을 삭제하지 않고 같은ID로 상태를 확인한다.
- 네트워크가 자주 끊기는1시간 업로드를 위해, 후속 단계에서 서버가 확인한 바이트 위치부터 이어 올리는 기능을 추가한다. 청크 순서·중복 전송·최종 크기와 해시 검증을 함께 시험한다.
