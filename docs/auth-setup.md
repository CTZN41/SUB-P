# ShotLog 로그인 연결 안내

> 2026-11-05 현재 결정: 네이버 로그인은 운영 배포 시 재추가한다. 현재 로그인·회원가입 화면과 제공사 목록에서는 제외했고, 서비스의 네이버 연결 경로도 등록하지 않는다. 아래 네이버 설정 설명은 향후 배포 준비용 참고로만 남긴다. 구글·카카오·이메일 로그인은 유지한다. 재추가 시 공개 HTTPS 연결 주소, 단일/다중 프로세스 state 보관 방식, 실제 계정 로그인·취소·재로그인을 확인해야 한다.

기준일: 2026-11-04. 사용자가 Google·카카오 로그인 시험 성공을 보고했다. 닉네임 중복 방지와 이메일 등록은 아래 최신 후속 기록을 따른다. 실제 이메일 인증 수신·추가 화면 조작은 별도 사용자 검증이 남아 있다. 비밀 키를 채팅이나 Git에 올리지 않는다.

## 지금 확인할 화면

- 로그인: http://127.0.0.1:5173/login
- 회원가입: http://127.0.0.1:5173/signup
- 설정 전에는 연결 준비 안내가 나오고 실제 가입·간편 로그인 요청 버튼은 비활성화된다. 기존 로컬 분석은 계속 사용할 수 있다.

## 1. 먼저 Supabase 값 두 개 준비

사용 중인 Supabase 프로젝트의 Settings → API Keys에서 아래 값을 확인하고 **backend/.env 맨 아래**에 입력한다. 데이터베이스 비밀번호나 OpenAI 키와 다른 값이다.

| 항목 | 입력할 값 |
|---|---|
| SUPABASE_URL | 프로젝트 URL. 예: https://프로젝트식별자.supabase.co |
| SUPABASE_PUBLISHABLE_KEY | 공개용 publishable 키 또는 이전 형식 anon 키 |
| AUTH_FRONTEND_ORIGIN | 지금은 http://127.0.0.1:5173 |

`service_role`·secret 키는 공개용 키 자리에 넣지 않는다. 코드에서 해당 키를 거절하며, 공개용 URL/키만 브라우저에 전달한다. 세 제공사의 Client Secret은 프론트 코드나 VITE_ 환경변수에 넣지 않는다.

Supabase Authentication → URL Configuration에서 Site URL은 `http://127.0.0.1:5173`로 설정하고 다음 두 Redirect URL을 허용한다.

- http://127.0.0.1:5173/auth/callback
- http://localhost:5173/auth/callback

이메일 가입은 Supabase의 이메일 제공사를 사용한다. 이메일 확인을 켜 두고 비밀번호 최소 길이를8자 이상으로 설정한다. 실제 사용자에게 보낼 때는 발신 메일/SMTP와 발송 제한도 준비한다. 회원가입은 이메일·비밀번호·비밀번호 확인만 입력하며, 인증 메일을 확인한 뒤 로그인한다.

### Google 계정과 같은 이메일로 이메일 회원가입을 하는 경우

Google로 이미 가입한 주소에 다시 signUp을 호출해도 이메일 로그인 비밀번호가 추가되지 않는다. 확인 완료 계정에는 실제 가입·메일 발송을 하지 않고 성공 형태의 응답을 돌려줄 수 있어, 화면에서는 발송을 단정하지 않도록 수정했다. 같은 계정에 이메일 로그인을 추가하려면 간편로그인 후 **내 프로필 → 이메일 로그인 비밀번호 → 비밀번호 등록**을 사용한다. 2026-11-04 이 기능을 추가했다. 실제 비밀번호 입력·로그아웃 후 이메일 로그인은 사용자가 직접 확인한다.

2026-11-04 사용자는 Google 로그인·로그아웃·재로그인을 성공으로 확인했다. 같은 주소의 이메일 재가입 때는 DB에 새 계정이나 인증 발송 요청 시각이 없었고 기존 계정에는 Google 연결만 있었다. 새 이메일의 메일 수신까지 확인한 것은 아니다.

기본 Supabase 메일 발송 서비스는 프로젝트 조직의 팀원 주소와 시간당 발송 한도를 제한한다. 다른 주소로 실제 가입·수신을 시험하기 전 SMTP 설정을 확인한다. 이 조사를 위해 이메일 확인을 끄거나 계정을 삭제·직접 확정하지 않았다. 공식 근거: [중복 가입 처리](https://github.com/supabase/auth/blob/master/internal/api/signup.go), [기본 메일 서비스의 제한](https://supabase.com/docs/guides/auth/auth-smtp).

## 2. Google 앱 만들기

1. Google Cloud의 Google Auth Platform에서 ShotLog 앱과 OAuth 웹 클라이언트를 만든다.
2. 필요한 범위는 기본 프로필·이메일·openid다. 테스트 기간에는 자신의 계정을 테스트 사용자로 등록한다.
3. Supabase Authentication → Sign In / Providers → Google에 표시되는 **Callback URL**을 Google의 승인된 리디렉션 URI에 등록한다. 위의 프론트 주소와 다른, Supabase의 주소다.
4. Google이 발급한 Client ID와 Client Secret은 Supabase의 Google 설정에 입력하고 제공사를 켠다.
5. backend/.env의 `AUTH_GOOGLE_ENABLED=true`로 바꾼다.

## 3. 카카오 앱 만들기

1. Kakao Developers에서 ShotLog 앱을 만들고 카카오 로그인을 활성화한다.
2. REST API 키와 카카오 로그인 Client Secret을 준비한다.
3. Supabase Kakao 제공사에 표시되는 Callback URL을 카카오의 Redirect URI에 등록한다.
4. 키와 Secret을 Supabase의 Kakao 설정에 입력한다. 필요한 프로필 동의 항목을 설정한다.
5. 이메일 제공 권한이 없는 앱이라면 account_email을 요청하지 않고 Supabase Kakao의 **이메일 없는 사용자 허용**을 켠다. 이메일을 임의로 만들거나 인증됐다고 표시하지 않는다.
6. backend/.env의 `AUTH_KAKAO_ENABLED=true`로 바꾼다.

### 2026-11-04 카카오 설정 상세·이메일 권한 주의

현재 로컬 코드에서 카카오 버튼의 연결 경로는 준비되어 있지만 `AUTH_KAKAO_ENABLED`는 false다. 이번에는 설정 안내와 코드 확인만 했으며, 개발자 앱 생성·Supabase 설정 저장·실제 카카오 로그인은 하지 않았다.

1. Kakao Developers의 앱 목록에서 ShotLog 앱을 생성한다. 앱 정보는 실제 개발 주체에 맞춰 입력한다. 기존에 같은 앱이 있으면 재사용한다.
2. 선택한 앱의 **카카오 로그인 → 사용 설정**을 ON으로 저장한다. REST API 기반 Supabase 연결을 사용하므로 별도의 카카오 JavaScript SDK나 OpenID Connect를 임의로 추가하지 않는다.
3. Supabase 프로젝트의 **Authentication → Sign In / Providers → Kakao**에서 Callback URL을 복사한다. 형식은 `https://<project-ref>.supabase.co/auth/v1/callback`이다. 현재는 클라우드 Supabase를 사용하므로 Supabase CLI용 localhost:54321 주소가 아니다.
4. Kakao 앱의 **앱 → 플랫폼 키 → 사용할 REST API 키** 상세에서 **카카오 로그인 Redirect URI**에 위 Callback URL을 붙여 넣고 저장한다. 같은 키의 **카카오 로그인 Client Secret** 발급·활성화 상태를 확인한다. REST API 키는 Supabase의 Client ID, 해당 Client Secret은 Supabase의 Client Secret에 입력한다. 앱 숫자 ID·JavaScript 키·어드민 키와 혼동하지 않는다.
5. 카카오의 **카카오 로그인 → 동의항목**에서 요청할 닉네임·프로필 사진·이메일 권한을 확인한다. 권한이 없는 이메일 항목을 임의로 요청하거나 사업자 정보를 만들어 넣지 않는다. 서비스 닉네임은 카카오 이름과 별도로 로그인 후 설정한다.
6. Supabase Kakao 제공사를 켜고 키·Secret을 입력해 저장한다. 이메일을 받지 않는 경우 공식 안내의 **Allow users without an email** 옵션을 켜되, 아래 기본 scope 문제까지 확인해야 한다.
7. Supabase **Authentication → URL Configuration**의 Site URL은 `http://127.0.0.1:5173`, Redirect URLs에는 `http://127.0.0.1:5173/auth/callback`와 `http://localhost:5173/auth/callback`를 유지한다. 이 프론트 주소와 카카오에 등록할 Supabase Callback URL은 역할이 다르다. 기존 Google 설정은 변경하지 않는다.
8. 원격 설정 완료를 확인한 뒤 로컬 `.env`의 `AUTH_KAKAO_ENABLED=true`를 적용하고 백엔드를 재시작한다. 앱에 실제 표시되는 버튼과 카카오 인가 요청 권한을 확인하고 로그인→서비스 닉네임→내 프로필→로그아웃→재로그인을 시험한다. 실제 이메일 없는 계정에는 이메일 비밀번호 등록을 제공하지 않는다.

**5번의 이전 단순 안내에 대한 정정:** Supabase 가이드는 account_email을 생략하는 이메일 없는 로그인을 안내하지만, 2026-11-04 확인한 공개 Auth 제공사 코드는 기본 scope에 `account_email`, `profile_image`, `profile_nickname`을 포함하고 사용자 추가 scope를 덧붙인다. 따라서 프론트에서 닉네임 scope만 지정하거나 이메일 없는 사용자 허용을 켜는 것만으로 이메일 요청이 제거된다고 보장할 수 없다. 현재 ShotLog 프론트는 scope를 별도로 지정하지 않는다. 실제 호스팅 프로젝트의 배포 버전·설정은 공개 master 코드만으로 확정하지 않는다.

이메일 권한이 없는 앱에서 KOE205가 나오면 실제 인가 URL의 요청 항목과 카카오 앱 권한을 대조한다. 필요한 경우 정당한 이메일 제공 권한 확보 또는 검증 가능한 사용자 지정 OAuth 연결을 별도 구현·시험해야 한다. 이메일을 가짜로 만들거나 인증 완료로 바꾸는 우회는 사용하지 않는다. KOE004는 사용 설정, KOE006은 Redirect URI 일치를 우선 확인한다.

공식 근거: [Supabase Kakao 설정](https://supabase.com/docs/guides/auth/social-sign-in/auth-kakao), [Kakao 설정하기](https://developers.kakao.com/docs/ko/kakaologin/prerequisite), [Supabase Auth 제공사 구현](https://github.com/supabase/auth/blob/master/internal/api/provider/kakao.go). 다음 확인은 사용자의 앱·권한 설정 후 실제 인가 요청과 로그인을 확인하는 것이다. 이번 문서 보완에서 서비스 코드·원격 설정·기존 계정은 변경하지 않았다.

2026-11-04 카카오 후속: 실제 프로젝트의 기본 인가 요청이account_email을 포함해KOE205가 발생했다. 현재 호스팅 Auth에서는 `queryParams.scope=profile_nickname`을 전달하면 기본 이메일·사진 권한을 대체함을 실제302 Location의scope만 읽어 확인했다. 표준 `scopes`는 기본 권한에 추가되어 해결되지 않았다. ShotLog 카카오 요청에만 이 옵션을 반영했으며 state·redirect_uri·client_id·PKCE를 덮어쓰지 않는다. 공식 공개master와 호스팅 버전 동작이 다를 수 있으므로 배포 변경 시 다시 검사한다. 사용자 로그인 시험 성공 보고를 받았고, 에이전트가 사용자 자격정보를 입력하거나 실제 로그인한 것은 아니다. 앞의 ‘별도 연결이 필요할 수 있음’은 조사 당시 가능성이며 현재 프로젝트는 이 축소 요청으로 시험했다.

## 4. 네이버 앱과 사용자 지정 연결

네이버는 Supabase의 기본 Google/Kakao 항목처럼 바로 선택하는 방식이 아니다. 네이버의 중첩 프로필과 토큰 교환용 state를 처리하는 연결 코드를 FastAPI에 준비했다.

**중요:** Supabase 서버가 이 연결 주소를 호출하므로 네이버 연결에는 외부에서 접근할 수 있는 HTTPS API 주소가 필요하다. 현재 PC의127.0.0.1은 Supabase가 접근할 수 없다. 실제 네이버 계정 로그인은 API 주소와 앱 설정이 준비된 다음 검증한다. 이번 작업에서 서버를 공개하거나 터널을 만들지는 않았다.

1. NAVER Developers에서 네이버 로그인 앱을 만든다.
2. Client ID와 Client Secret을 backend/.env의 `NAVER_CLIENT_ID`, `NAVER_CLIENT_SECRET`에 입력한다.
3. Supabase Auth Providers → New Provider에서 Manual OAuth2 연결을 만든다. 식별자는 `custom:naver`, 이름은 네이버로 지정한다.
4. Supabase에 표시된 Callback URL을 네이버 앱의 Callback URL과 backend/.env의 `NAVER_REDIRECT_URI`에 동일하게 입력한다.
5. 사용자 지정 제공사에는 다음을 입력한다. 아래 API주소는 실제 외부 HTTPS 주소로 바꿔야 한다.

| Supabase 제공사 항목 | 입력 |
|---|---|
| Identifier | custom:naver |
| Client ID / Client Secret | 위 네이버 앱의 값. Supabase 설정에도 직접 입력 |
| Authorization URL | https://API주소/api/auth/naver/authorize |
| Token URL | https://API주소/api/auth/naver/token |
| UserInfo URL | https://API주소/api/auth/naver/userinfo |
| PKCE | 켜기. S256 사용 |
| Email optional | 켜기 |
| Scopes | 불필요한 추가 범위를 요청하지 않음 |

6. 네이버 프로필에서는 계정의 고유ID와 선택한 닉네임을 사용한다. 임의 이메일 인증이나 이메일만으로 계정 합치기를 하지 않는다.
7. 제공사를 활성화하고 backend/.env의 `AUTH_NAVER_ENABLED=true`로 바꾼다.

네이버 연결의 일회용 state는 현재 FastAPI 한 프로세스의 메모리에서10분 보관한다. 재시작하면 진행 중 연결은 다시 시작해야 한다. **여러 작업 프로세스/서버로 배포하기 전에는 Redis 등 공유 저장소로 바꾸고 호출 제한을 검증해야 한다.** 실제 네이버↔Supabase 인증서버 조합은 아직 검증하지 않았다.

## 5. 로그인 보호 켜기

연동할 제공사만 먼저 켤 수 있다. 예를 들어 Google만 준비됐다면 나머지 두 제공사는 false로 둔다.

1. 저장소의 DB 변경은 `20261103_0006`까지 적용했다. 분석 소유자 항목을 추가했고, Supabase Data API가 공개용 키로 분석·선수·슛·작업 테이블을 직접 읽지 못하도록 RLS를 켰다. 기존 기록을 임의 계정에 배정하거나 삭제하지 않았다.
2. 다른 PC/새 DB에서는 backend 폴더에서 `.venv\Scripts\python.exe -m alembic upgrade head`를 먼저 실행한다.
3. 위 값과 제공사 설정이 준비되면 `AUTH_REQUIRED=true`로 변경하고 백엔드를 다시 실행한다. 프론트도 새로고침한다. **이번 작업에서는 현재 백엔드를 종료·재시작하지 않았다.**
4. 현재 웹 서버가 이전 코드로 실행 중이면 인증 API가 없으므로 개발 화면에는 준비 상태만 나온다. 빌드·DB 준비와 실제 실행 반영을 구분한다.
5. 로그인 보호를 켜면 비로그인 접근은 로그인 화면으로 이동한다. 서버도 세션을 Supabase에서 검증하고 목록·원본 영상·슛·월별 결과·수정·삭제를 소유자별로 제한한다.

소유자가 없는 기존 로컬 기록은 자동으로 새 사용자에게 넘기지 않는다. 로그인 전환 후 필요하면 본인 소유 여부를 확인하고 별도 이전해야 한다. 서로 다른 제공사의 계정을 자동으로 같은 계정으로 합치지 않는다.

## 6. 실제로 확인할 순서

1. 이메일 가입 → 메일 인증 → 로그인 → 새로고침 → 로그아웃.
2. Google → 카카오 → 네이버 각각 로그인과 동의 취소·돌아오기.
3. 다른 계정2개로 목록·월별 집계·영상·개별 결과가 서로 보이지 않는지 확인.
4. 계정 A가 만든 시험 영상을 계정 B에서 직접 주소로 열거나 수정·삭제할 수 없는지 확인.

### 2026-11-04 닉네임 고유 등록·이메일 추가 (최신 동작)

- **인증 대기:** 요청 성공과 등록 완료를 구분한다. 대기 주소를 표시하고 ‘등록 상태 확인’으로 서버를 다시 읽는다. 이메일 확인 전에는 비밀번호 등록을 허용하지 않는다. Gmail 점/플러스 별칭을 일괄 같은 주소로 바꾸지는 않는다.
- **DB 적용:** 마이그레이션 `20261104_0007`은 고유 프로필 테이블과 RLS를 추가하고 기존 닉네임을 가입 순서대로 이전한다. 브라우저가 테이블에 직접 쓰는 정책은 만들지 않았다. Auth 메타데이터·기존 분석 기록은 보존한다.
- **검증:** 백엔드 전체 243개, 프론트 40개 시험과 빌드 통과. 기존 린트 경고 4개는 남는다. DB에서 가입 순서별 이전 일치·고유 키 중복 0개·RLS를 확인했다. 실제 메일 발송·메일 링크 확인·Chrome 렌더링은 실행하지 않았다.
- **사용자 확인 순서:** 새로고침 → 사용 중인 닉네임 거절 → 새 이름 저장 → 재로그인 유지 → 이메일 없는 계정의 프로필에서 기존 이메일 거절 → 새 주소로 인증 메일 요청 → 링크 확인 → 등록 상태 확인 → 인증 후 비밀번호 등록 가능 여부 확인. 기존 주소는 재가입 대신 기존 로그인 방법을 사용한다.
- **실행 확인:** 백엔드 재시작과 프론트 변경 반영을 확인했다. 실제 PostgreSQL/5173 프록시에서 이메일·닉네임 중복은 각각 409, 미사용 정보 조회는 200, 비로그인 프로필은 401이었다. 빈 제외 ID의 PostgreSQL 자료형 오류를 수정하고 인증 시험 34개를 다시 통과했다. 메일 발송·계정 생성은 하지 않았다.

공식 근거: [로그인한 사용자 이메일 수정](https://supabase.com/docs/reference/javascript/auth-updateuser), [Auth의 이메일 중복 검사](https://github.com/supabase/auth/blob/master/internal/api/user.go). 이번 구현에서 원격 제공사 설정이나 이메일 인증 요구를 변경하지 않았다.

### 2026-11-06 간편로그인 취소 후 재시도 복구

- 원인: 간편로그인 시작 시 연결 중 상태를 켜고 오류일 때만 해제했다. 제공사 화면 이동이 정상 반환된 뒤 취소/뒤로가기로 돌아오면 버튼 잠금이 남을 수 있었다. 설치된 Supabase SDK가 이동 URL을 만든 뒤 즉시 반환하는 동작을 확인했다.
- 변경: SDK에서 이동 URL을 받은 후 앱이 이동하고, 성공/실패 모두 요청 잠금을 해제한다. OAuth 화면에서 복귀하는 pageshow/focus에도 잠금을 해제하되 이메일 로그인이나 URL 준비 중에는 해제하지 않는다. 중복 간편로그인 클릭을 막고 취소 콜백의 원래 목적지도 유지한다. 세션/닉네임/로그인 유지 선택을 삭제하지 않는다.
- 검증: 프런트62개 자동시험·타입검사·빌드 통과. 실제 SDK의 재시도마다 새 PKCE 인증값 생성도 확인했다. 별도 Chrome에서 실제 AuthPage 컴포넌트와 모의 제공사 응답으로 취소/뒤로가기/반복 시도·대기 중 중복 방지·오류/예외/URL 누락 복구·이메일 대기 잠금·콜백 목적지 보존5묶음을 확인했다. 실제 제공사/백엔드 요청0이다.
- 범위: 사용자 실제 Google·카카오 동의 취소와 재로그인은 미검증이며, 현재 화면을 새로고침한 뒤 확인할 수 있다. 백엔드/DB/모델/더미는 이번 로그인 수정에서 변경하지 않는다. 기존 백엔드746개 통과는 앞선 버전의 검증 이력이며 이번 프런트 수정으로 전체 백엔드 시험을 반복하지 않았다.
