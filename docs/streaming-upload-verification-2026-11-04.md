# 10GB 업로드 직접 저장 구현과 재시험

2026-11-04 사용자가 중복 저장 개선을 구현하고 같은10GB 파일로 시간·공간을 비교하도록 요청했다. 이후 AI 후보 판단·심층 분석·결과 저장까지200~500개 후보의 부하 검증을 추가했다.

## 업로드 구현

- `POST /api/uploads`에서 사용자별 업로드ID를 만들고 이름·촬영 날짜·확장자·크기·동의·디스크 여유를 확인한다.
- `PUT /api/uploads/{id}`는 요청 스트림을 청크로 받아 `.incoming/{id}/original.part` 하나에 기록한다. 실제 누적 바이트를 검사하고 디스크 쓰기·마지막 flush/fsync는 작업 스레드에서 수행한다.
- `POST /api/uploads/{id}/complete`에서 영상 정보를 확인하고 같은 볼륨의 최종 위치로 rename한다. 기존 등록·선수·재생용 변환 로직을 공유해 DB에 저장한다.
- 파일·등록 정보는 업로드 소유 계정에 묶고, OS 잠금으로 같은 업로드의 동시 처리 충돌을 막는다. 완료 재시도는 동일 분석ID를 반환한다. DB 커밋 응답이 유실돼도 파일을 보존하고 재시도로 DB 상태를 확인한다.
- 전송 중단·용량 초과·공간 부족이면 부분 파일을 정리한다. 재시작 때 중단된 수신을 정리하고48시간 지난 미완료 파일을 만료 처리한다. DB 확정 여부를 확인해야 하는 파일은 보존한다. 등록 기록 삭제 시 업로드 세션 정보도 함께 정리한다.
- 프론트는 정보 확인→파일 전송→등록 완료 순서로 호출한다. 완료 응답 오류 뒤 같은 화면에서 재시도하면 업로드ID를 재사용해 파일 재전송과 기록 중복을 줄인다. 실행 중인 이전 백엔드에는 기존 multipart 등록으로 연결한다.
- 기존 multipart 경로도 수신 중 총 요청 크기를 제한한다. 파일 제한에64KiB의 폼 부가 영역을 더한 상한이며 실제 파일 제한은 등록 함수에서도 검사한다.

## 같은10GB 파일의 재측정

입력은 앞선 시험과 SHA-256이 같은1시간1080p/약60fps H.264 반복 파일이다. 실제 미디어6.59GB에 MP4 여분 영역3.41GB를 더해 정확히10,000,000,000바이트로 만들었다. localhost:8011·별도 SQLite·시험용65분/12GB 조건을 사용했다. 기존8000/5173과 진행 중인33분 분석을 중단하거나 재시작하지 않았다.

| 등록 전체 시간 |47.98초|37.82초|37.41초|

개선 방식 평균은37.62초로, 같은 재시험의 기존47.98초보다10.37초·21.6% 단축됐다. 동시 디스크 표본은약49.7% 감소했다. 원본 파일1개분과 작은 세션 메타데이터만 남는 구조를 확인했다. 파일 생성·사후 전체 해시 검사는 등록 시간에서 분리했다.

최초 기존 측정81.66초와 비교하면53.9% 감소하지만, 기존 방식도 재측정에서47.98초로 달라졌다. 캐시와 같은 PC의 다른 분석 부하가 달라질 수 있어, 본 비교의 주된 속도 개선 수치는 방금 재측정한 기존 방식 대비21.6%로 보고한다. 개선2회와 기존 재측정1회의 작은 표본이다.

현재5GiB 제한의 사전 검사에서는 파일 본문 전송0바이트·디스크 기록0바이트로 약0.014초에413을 받았다. 기존69.81초 거절은10GB 전체 수신 후 파일 제한에 도달한 결과였다. 본문 전송이 없었던 새 거절 사례에는 전송 처리량을 계산하지 않았다.

## 무결성과 오류 복구

- 개선2회 모두 저장10GB 전체 SHA-256이 입력과 일치했다. 앞·5GB 지점·끝64KiB의 HTTP Range206과 바이트 일치,00:00·15:00·30:00·45:00·59:58의 각30프레임 읽기도 통과했다.
- 전송 중단·잘못된 길이·헤더 없는 실제 초과·507 공간 부족·다른 계정 접근·동시 수신·중복 완료·DB 커밋 전후 오류·재시작 정리·만료·삭제 후 재등록 방지를 회귀 시험했다.
- 백엔드 전체520개가 통과했다. 이후 마이그레이션·공간 부족·기존 커밋 후 조회 실패의3개 회귀 시험을 추가했고, 삭제 경로를 보완한 뒤 관련38개를 재확인했다. 프론트48개와 빌드가 통과했다.
- 반복 측정 뒤 생성한10GB 저장본3개만 정리했다. 시험 원본과 개선1회 저장본은합계약20GB로 별도 작업 폴더에 보관한다. 사용자 Downloads 원본과 운영 기록은 정리 대상에서 제외했다.

## 적용 상태와 DB 크기 항목

코드·프론트 연결과 별도 시험 서버에서의 검증을 완료했다. 기존 분석 완료 후 활성 작업0개를 확인하고 새 백엔드를 반영했다.8000/5173이200으로 응답하고 새 업로드3개 경로의 노출과 미로그인 업로드401을 확인했다. 새 경로의 실제 Chrome 조작은 후속 확인 항목이다.

운영 PostgreSQL의 `analyses.file_size`가32비트 `integer`임을 읽기 전용 조회로 확인했다. 약2GB보다 큰 크기를 저장할 수 있도록 모델을 `BigInteger`로 변경하고 `20261104_0008` 마이그레이션을 추가했다. 별도 DB에서10GB 크기의 행 보존·타입 변경을 검증했고, 기존 분석이 완료된 뒤 운영에도 적용했다. 운영 `bigint`와 버전0008을 재조회했다. 기존 분석4개·슛312개가 유지됐고 이번247개 슛의 ID·시각·좌표·결과·상태 fingerprint가 반영 전후 일치했다. 서비스의 길이/용량 제한은40분·5GiB이며10GB 시험에는 별도 확대 설정을 사용했다.
