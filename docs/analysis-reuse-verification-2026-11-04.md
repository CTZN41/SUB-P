# 후보 분석 중복 연산·AI 요청 재사용 검증

## 적용 범위와 결정

- 사용자의 최종 요청대로 현재 화면 구성, 후보 추출 규칙, 구간 길이, 70% 위치 확정 기준을 유지한다. 변경 대상은 후보 탐지·재검증·추가 AI 검토 내부다.
- `슛 여부 확인 필요` 카드 추가는 철회했다. 사용자가 선택한 정책에 따라 AI가 비슛으로 확정한 후보를 결과에서 제외한다. 비슛 기준은 완료된 슛 검증의 `not_shot`, 신뢰도 90% 이상이며, 후속 AI가 실제 슛이라고 판단한 충돌 사례는 제외하지 않는다. 애매한 응답과 사용자 확인 기록도 유지한다.

## 구현

1. 재탐지·발 추적에서 같은 원본 프레임의 객체·자세 관측을 재사용한다. 영상 식별값, 실제 픽셀 해시, 모델, 입력 크기·신뢰도·대상 클래스·실행 장치가 일치해야 한다. 프레임 식별값은 프레임당 한 번 계산하며 시간 순서에 따른 선수·골대 추적은 다시 수행한다. 관측값 저장은 64MiB 직렬화 데이터와 75,000항목 상한을 둔다. 전체 원본 프레임을 캐시에 저장하지 않는다.
2. 같은 후보 시각·같은 검증 구간의 슛 여부 요청은 이미지 준비부터 재사용한다. 일반 검증과 앞 구간 검증은 별개다. 다른 질문, 이미지, 모델, 응답 형식의 AI 요청은 합치지 않는다. 같은 요청이 동시에 들어오면 한 번만 실행하며 서로 다른 후보의 병렬 처리는 유지한다.
3. 완료한 로컬 탐지·후보 검증·구도 확인 단계와 정상 AI 응답을 원자적으로 중간 저장한다. 실패 또는 AI 부분 실패 후 기존 분석 시작 흐름으로 다시 실행하면 일치하는 완료 단계·응답을 재사용하고 실패 요청은 다시 시도한다. 정상 완료한 분석의 새 재분석은 새 실행으로 처리한다. 영상·모델·기준점·분석 코드·설정이 바뀌면 이전 중간 결과를 재사용하지 않는다.
4. 신규 호출 토큰과 재사용 응답의 과거 토큰을 구분한다. 최상위 `api_usage`는 이번 실행의 신규 호출 사용량이며, 타임아웃으로 알 수 없는 사용량은 `api_usage_complete=false`로 표시한다. 누적 API 호출 시간은 병렬 전체 경과와 다르다.
5. 비슛 확정 후보는 신규 슛 저장과 기존 결과 조회·월별 통계에서 제외한다. 기존 DB를 일괄 삭제하지 않는다. 제외 원인과 원래 후보는 진단 자료에 남긴다. 내부 진단에는 AI 실패·슛 미확정·득점 미확정·위치 미확정·종류 미확정 원인을 분리한다.

## 실제 영상 전후 시간

동일한 기존 원본의 짧은 구간에 기본 15fps, 겹치는 30fps 재탐지, 15fps 발 재추적을 순서대로 실행했다. 모델 초기 준비는 측정에서 제외했고 유료 API 호출·DB 수정은 하지 않았다. 이전 방식 비교는 관측 캐시를 꺼서 해시·캐시 저장 비용도 발생하지 않게 했다.

| 원본·시험 구간 | 재사용 전 | 재사용 후 | 단축 | 관측 재사용 | 결과 비교 |
|---|---:|---:|---:|---:|---|
| 야외 720p·30fps, 16~24초 | 32.5166초 | 18.7837초 | 42.23% | 630/1,450 | 후보·전체 발 추적 결과 동일 |
| 1080p·60fps, 6~14초 | 17.0511초 | 11.9705초 | 29.80% | 429/1,018 | 후보·전체 발 추적 결과 동일 |

- 야외 재탐지 15.9030→8.5340초, 발 재추적 6.1147→0.3804초. 각 단계의 발 관측 32·58·29개가 유지됐다.
- 1080p 재탐지 8.2584→4.9456초, 발 재추적 3.0766→0.7921초. 각 단계의 발 관측 32·64·32개가 유지됐다.
- 단일 짧은 구간의 연산 비교다. 겹치는 프레임이 적으면 효과가 작으며, 최초 계산에는 캐시 관리 비용이 추가된다. 독립적인 슛 정답 정확도나 33분 전체 AI 포함 단축률로 해석하지 않는다.
- 원자료: `backend/evaluation/results/analysis-reuse-2026-11-04.json`, `analysis-reuse-1080p-2026-11-04.json`. 재현 스크립트: `backend/scripts/verify_analysis_reuse.py`.

## AI·복구 검증과 한계

- 모의 API로 동일 동시 요청의 단일 호출, 응답 변형 격리, 질문·모델·이미지 변경 시 재호출, 실패 응답 재시도, 구간별 검증 분리를 확인했다.
- 실제 작업 실행 함수를 SQLite 시험 환경에서 중단시킨 뒤 다시 실행했다. 로컬 탐지·후보 검증은 각 1회만 실행됐고 완료한 첫 AI 응답을 재사용했다. 남은 요청만 신규 사용량으로 집계됐다. 유료 API를 호출한 시험은 아니다.
- 기존 247개 응답을 복사해 정책을 대조하면 비슛 확정 69개가 제외되고 178개가 남는다. 남은 AI 응답은 성공 80·실패 85·득점 미확정 12·AI 실패 1이다. 이는 기존 응답의 분류 검증이며 새로운 정답 정확도 측정이 아니다.
- 기존 247개 사례에는 후보 하나가 위치 일관성 질문을 여러 번 받은 경우가 없었다. 독립적인 3점 영상 검토와 좌표 검토는 다른 질문이므로 삭제하지 않았다. 새 AI 호출 자체의 응답 속도와 전체 분석 시간은 후속 전체 실행에서 확인해야 한다.
- 중간 저장은 이후 실행부터 생성된다. 이 변경 전에 수행한 분석에 새 중간 응답을 소급 생성하지 않는다. 응답 수신 직후 저장 전에 프로세스가 종료되면 그 요청은 다시 필요할 수 있다.

## 다음 확인

- 기존에 사용하던 긴 영상 한 번을 실행해 실제 재사용 적중 수·단계 시간·신규 토큰·확인 필요 개수를 비교한다.
- 별도 3점/득점 검토의 통합은 동일 정답표를 이용한 비교가 확보된 뒤 판단한다. 현재 증거·신뢰도 조건을 낮추지 않는다.
