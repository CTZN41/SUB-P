# ShotMap AI 개발 계획(PLAN)

## 1. 문서 목적

이 문서는 `mvp.md`, `PRD.md`, `spec.md`에 정한 ShotMap AI를 어떤 순서로 개발할지 설명합니다.

각 Phase는 앞 단계에서 만든 결과를 다음 단계가 사용하는 구조입니다. 한 Phase를 끝낼 때마다 기능을 직접 확인하고, 완료한 내용과 남은 문제를 기록한 뒤 다음 Phase로 이동합니다.

첫 버전의 공식 완료 판단은 개인 연습 영상으로 진행합니다. 3대3은 선수 등록, 지정, 수정과 선수별 결과 흐름을 완성하지만 자동 선수 구분 정확도는 참고 결과로 기록합니다.

## 2. 개발 순서 요약

| Phase | 이름 | 핵심 결과 |
|---|---|---|
| 0 | 범위·기술·시험 준비 | 실행 구조, 데이터 저장 방식, 테스트 영상과 정답표 확정 |
| 1 | 프로젝트 뼈대와 로컬 저장 | 프로그램 실행, 기본 화면 이동, 데이터와 영상 보관 |
| 2 | 데이터 구조·좌표·통계 | 분석·선수·슛 저장, 14개 구역과 통계 계산 |
| 3 | 영상 등록과 기본 검사 | MP4 선택, 제한 검사, 메타정보와 동의 저장 |
| 4 | 코트 위치 맞추기 | 기준점 보정과 영상 좌표의 코트 좌표 변환 |
| 5 | 선수 설정 | 개인 선수와 최대 6명의 선수 등록·화면 지정 |
| 6 | 분석 작업 흐름 | 시작, 진행 상태, 취소, 실패, 다시 시도 |
| 7 | 영상 분석 기초 | 선수·공·골대 추적과 슛 후보 생성 |
| 7A | Supabase 저장소 전환 | 기존 SQLite 데이터는 보존하고 PostgreSQL에 새 데이터를 저장 |
| 8 | 슛 결과와 OpenAI 보조 | 위치, 성공·실패, 슛 종류, 전체 시퀀스 저장 |
| 9 | 검토·수정·재생 | 확인 목록, 슛 추가·수정·삭제, 장면 재생 |
| 10 | 결과 화면과 2D 히트맵 | 요약 통계, 필터, 14개 존 히트맵 |
| 11 | 3D 슈팅 맵 | 3D 반코트, O/X 표시, 선택과 카메라 조작 |
| 12 | 기록 보관·삭제·복구 | 최근 기록, 재실행 보존, 안전한 삭제와 오류 복구 |
| 13 | 3대3 기능 | 선수 A~F, 화면 지정, 슈터 수정, 선수별 결과 |
| 14 | 정확도·성능·발표 준비 | 목표 정확도 측정, 처리 시간 기록, 최종 시나리오 통과 |

## 3. 공통 작업 원칙

- 한 Phase에서 정한 완료 기준을 통과한 뒤 다음 Phase로 이동합니다.
- 화면보다 데이터 저장과 계산 규칙을 먼저 만듭니다.
- 자동 분석이 확실하지 않으면 결과를 숨기지 않고 `확인 필요`로 남깁니다.
- 원본 영상 전체를 OpenAI에 보내지 않고 필요한 슛 후보 장면만 사용합니다.
- API 키와 비밀값은 환경설정 파일에만 보관하며 화면, 문서, 로그와 Git에 남기지 않습니다.
- 실제 측정 전에는 정확도, 처리 시간과 남은 시간을 확정값처럼 표시하지 않습니다.
- 자동화된 검사와 사람이 직접 보는 화면 검사를 함께 진행합니다.
- 각 Phase가 끝나면 문서의 진행 기록에 완료 항목, 확인 결과와 다음 작업을 남깁니다.

## Phase 0. 범위·기술·시험 준비

### 목표

개발을 시작하기 전에 프로그램의 구조와 시험 기준을 확정하여 중간에 전체 구조를 다시 만드는 일을 줄입니다.

### 진행 작업

1. 현재 PC의 운영체제, CPU, 메모리, 저장 공간과 영상 처리 가능 환경을 확인합니다.
2. PC에서 실행할 화면, 로컬 처리 프로그램, 로컬 데이터 저장소와 영상 저장 폴더의 역할을 나눕니다.
3. 화면과 분석 프로그램이 상태를 주고받는 방식을 정리한 SDD를 작성합니다.
4. 분석, 선수, 슛, 코트 기준점과 작업 상태의 데이터 구조를 확정합니다.
5. `등록 중`부터 `완료`, `실패`, `취소됨`까지 상태가 바뀌는 규칙을 그림으로 정리합니다.
6. OpenAI가 받을 입력과 돌려줄 결과 형식을 정하되 실제 키는 문서에 적지 않습니다.
7. 개발용 샘플 영상 두 개의 사용할 구간을 정합니다.
8. 각 샘플 구간에서 실제 슛 시간, 성공·실패, 대략적인 위치와 슛 종류를 사람이 먼저 기록합니다.
9. 최종 검증용 직접 촬영 영상의 촬영 계획을 세웁니다.

### 샘플 영상 사용 계획

- 샘플 A의 초반 구간: 슛 감지, 성공·실패와 위치 추정의 초기 시험
- 샘플 B: 긴 영상 처리, 진행 상태, 취소와 슛 종류 분류 시험
- 직접 촬영 영상: 최종 정확도, 14개 구역, 60fps 재생과 발표 검증

### 산출물

- 기술 설계 문서(SDD)
- 데이터 구조 초안
- 상태 변화표
- 샘플 영상 정답표
- 환경설정 예시 파일의 항목 목록

### 완료 기준

- 화면, 분석 프로그램, 저장소와 영상 폴더의 역할이 구분되어 있습니다.
- 두 샘플 영상에서 사용할 구간과 시험 목적이 기록되어 있습니다.
- 실제 비밀값 없이 OpenAI 설정 항목이 정의되어 있습니다.
- 다음 Phase에서 프로젝트 뼈대를 만들 때 필요한 선택이 남아 있지 않습니다.

## Phase 1. 프로젝트 뼈대와 로컬 저장

### 목표

아직 AI 분석이 없어도 프로그램을 실행하고 기본 화면을 이동하며 데이터를 저장할 수 있는 기반을 만듭니다.

### 진행 작업

1. 화면, 영상 처리, 데이터 저장과 테스트 영역을 분리한 폴더 구조를 만듭니다.
2. 한 번의 명령으로 개발용 프로그램을 실행할 수 있게 준비합니다.
3. 시작 화면, 새 영상 등록, 코트 확인, 선수 설정, 분석 진행, 결과와 기록 화면의 빈 틀을 만듭니다.
4. 화면 주소와 뒤로 가기 동작을 정리합니다.
5. 로컬 데이터 저장소를 준비하고 초기 구조를 자동으로 만들 수 있게 합니다.
6. 원본 영상, 임시 분석 파일과 결과 파일의 저장 폴더를 구분합니다.
7. 설정값이 없거나 저장 폴더를 만들 수 없을 때 이해하기 쉬운 오류를 표시합니다.
8. `.env`와 영상·분석 결과가 Git에서 제외되는지 확인합니다.

### 테스트

- 프로그램을 종료하고 다시 실행할 수 있는지 확인합니다.
- 모든 기본 화면으로 이동하고 새로고침해도 오류가 없는지 확인합니다.
- 로컬 저장소가 한 번만 준비되고 기존 내용을 덮어쓰지 않는지 확인합니다.
- 비밀 설정과 원본 영상이 Git 저장 대상에 나타나지 않는지 확인합니다.

### 완료 기준

- PC에서 프로그램을 실행하면 시작 화면이 열립니다.
- 모든 주요 화면의 빈 틀로 이동할 수 있습니다.
- 데이터와 영상 저장 위치가 준비되어 있습니다.
- 아직 구현되지 않은 기능은 동작하는 척하지 않고 준비 중으로 표시됩니다.

### 진행 결과 (2026-10-28)

- React + TypeScript + Vite 화면 프로젝트를 만들었습니다.
- 홈, 새 분석, 코트 설정, 선수 설정, 분석 진행, 결과, 기록 화면의 주소와 빈 틀을 준비했습니다.
- FastAPI 상태 확인 API와 SQLite 연결 기반을 만들었습니다.
- 원본 영상은 `backend/uploads`, 분석 임시 파일은 `backend/work`, SQLite는 `backend/data`에 나누어 보관하도록 준비했습니다.
- Alembic 기본 설정과 `.env.example`을 준비했습니다.
- 루트에서 `npm run dev` 한 번으로 백엔드와 프론트엔드를 함께 실행할 수 있습니다.
- 미구현 기능은 실제로 처리된 것처럼 보이지 않도록 준비 중 문구를 표시했습니다.
- 백엔드 자동 시험 2개, Alembic 실행, 프론트 린트와 배포 빌드, 실제 로컬 응답을 확인했습니다.
- 검증에 사용한 5173·8000 서버는 종료했습니다.

### YOLO26 사전 가능성 시험 (2026-10-28)

- 제공받은 두 MP4를 `backend/uploads`에 복사하고 원본 다운로드 파일은 보존했습니다.
- 최신 Ultralytics YOLO26의 소형 모델인 `yolo26n`과 CPU 전용 PyTorch 환경을 준비했습니다.
- 샘플 A `0:10~1:33`에서 초당 4장을 검사한 결과, 332장 중 사람은 303장, 공은 185장에서 탐지됐습니다.
- 샘플 B의 실제 슈팅 구간 `9:30~10:30`에서는 241장 중 사람은 241장, 공은 133장에서 탐지됐습니다.
- 샘플 B `9:30~9:38`을 초당 12장으로 다시 검사해 첫 슛의 릴리스 후보를 `9:31.917~9:32.083`로 찾았습니다.
- 기본 모델은 낮은 신뢰도에서 공이 아닌 물체를 공으로 잡거나, 공을 놓치는 프레임이 있어 자동 확정에는 사용할 수 없습니다.
- 영상 프레임 추출 도구, 사람·공 기본 탐지 도구와 초기 릴리스 후보 규칙을 추가했습니다.
- 다음 분석 단계에서는 농구공·림 학습 데이터와 사람 자세를 결합해 오탐과 누락을 줄여야 합니다.

### 남은 제한

- 실제 영상 등록과 데이터 테이블은 다음 Phase부터 구현합니다.
- FFmpeg와 영상 분석 패키지는 아직 설치하지 않았습니다.
- 화면별 새로고침은 빌드와 개발 서버 응답으로 확인했으며, 브라우저에서 모든 주소를 사람이 직접 눌러 보는 확인은 아직 하지 않았습니다.

## Phase 2. 데이터 구조·코트 좌표·통계 계산

### 목표

자동 분석 없이 예시 데이터를 넣어도 저장, 수정, 통계와 지도 표시용 결과를 정확히 만들 수 있게 합니다.

### 진행 작업

1. 분석 한 건의 정보와 상태를 저장합니다.
2. 선수의 이름, 등번호, 임시 이름과 최초 지정 위치를 저장합니다.
3. 슛의 시간, 시퀀스, 선수, 좌표, 구역, 성공 여부, 종류와 확인 상태를 저장합니다.
4. 코트 좌표 범위와 좌우 방향을 하나의 규칙으로 확정합니다.
5. 코트를 SPEC의 14개 구역으로 나누는 계산을 만듭니다.
6. 구역 경계 위 좌표가 항상 같은 구역에 들어가는 규칙을 정합니다.
7. 전체, 선수별, 슛 종류별, 구역별 시도 수와 성공률을 계산합니다.
8. 기록이 없을 때 `기록 없음`을 돌려주는 규칙을 적용합니다.
9. 저장된 요약값이 실제 슛 기록과 다르면 슛 기록을 기준으로 다시 계산합니다.

### 테스트

- 14개 구역의 중앙과 모든 경계 좌표를 시험합니다.
- 성공 0회, 시도 0회, 1회, 2회와 여러 회인 경우를 시험합니다.
- 선수를 바꾸어도 다른 선수 기록이 섞이지 않는지 확인합니다.
- 슛을 추가·수정·삭제한 뒤 모든 통계가 다시 맞는지 확인합니다.

### 완료 기준

- 예시 슛 데이터를 저장하고 다시 읽을 수 있습니다.
- 같은 좌표는 언제나 같은 구역에 들어갑니다.
- 통계 계산 결과가 사람이 계산한 값과 일치합니다.
- 이후 화면은 모두 같은 계산 기능을 재사용할 수 있습니다.

### 진행 결과 (2026-10-28)

- 분석, 코트 보정, 선수, 슛과 분석 작업을 저장하는 SQLAlchemy 모델을 만들었습니다.
- 첫 Alembic 변경 파일을 만들고 로컬 SQLite에 `20261028_0001`까지 적용했습니다.
- 표준 반코트를 가로 50ft, 베이스라인부터 하프라인 47ft로 고정했습니다.
- 골대 중심을 `(25, 5.25)`로 두고 SPEC의 14개 구역을 항상 하나로 계산하게 했습니다.
- 3점선·코너·제한구역·페인트존 경계의 고정 우선순위를 만들었습니다.
- 전체, 선수별, 슛 종류별, 구역별 시도·성공·실패·성공률을 슛 원본에서 다시 계산하게 했습니다.
- 시도 0회는 성공률을 `기록 없음`에 해당하는 `null`로 반환하고, 1~2회도 계산에 포함합니다.
- 저장·재조회, 14개 구역 대표점과 경계, 코트 밖 좌표, 통계 재계산을 포함한 백엔드 자동 시험 27개를 통과했습니다.
- Alembic 검사에서 추가로 만들 변경이 없음을 확인했습니다.

## Phase 3. 영상 등록과 기본 검사

### 목표

사용자가 MP4 한 개를 안전하게 등록하고 분석 전 필요한 정보와 동의를 저장할 수 있게 합니다.

### 진행 작업

1. 분석 이름, 영상 파일, 촬영 형태, 촬영 날짜와 선수 이름 입력 화면을 만듭니다.
2. 분석 이름의 앞뒤 공백을 제거하고 1~100자 조건을 검사합니다.
3. MP4 실제 형식, 최대 10분, 최대 5GB와 한 파일 조건을 검사합니다.
4. 파일 이름, 크기, 길이, 해상도와 fps를 읽습니다.

8. 정상 파일을 내부 영상 폴더에 안전하게 복사하고 상태를 `설정 필요`로 저장합니다.

## Phase 6. 분석 작업 흐름

### 목표

실제 AI 분석을 붙이기 전에 시작, 진행, 취소, 실패와 재시도 흐름을 안정적으로 만듭니다.

### 진행 작업

1. 분석 전 파일, 동의, 코트와 선수 설정을 최종 검사합니다.
2. `분석 시작`을 눌러야만 작업을 생성합니다.
3. 빠르게 여러 번 눌러도 한 작업만 만들어지게 합니다.
4. `대기 중`, `분석 중`, `검토 필요`, `완료`, `실패`, `취소됨` 전환을 구현합니다.
5. SPEC의 7단계 진행 상태와 처리한 영상 구간을 표시합니다.
6. 화면을 벗어나도 작업이 계속되고 최근 기록에서 다시 열 수 있게 합니다.
7. 취소 확인, 안전한 중단과 중간 결과 정리를 구현합니다.
8. 프로그램이 갑자기 종료된 작업을 다음 실행 때 감지합니다.
9. 실패 이유와 다시 분석 기능을 구현합니다.
10. 개발 초기에는 가짜 분석 작업으로 전체 흐름을 먼저 시험합니다.

### 테스트

- 분석 버튼 중복 클릭, 화면 이동, 취소와 재시도를 확인합니다.
- 분석 중 프로그램을 종료한 뒤 다시 실행합니다.
- 취소 후 원본과 설정은 남고 중간 슛은 사라지는지 확인합니다.
- 재시도 후 같은 슛 데이터가 중복되지 않는지 확인합니다.

### 완료 기준

- 실제 분석기가 없어도 작업 상태의 전체 흐름을 검증할 수 있습니다.
- 취소·실패 후에도 사용자가 원본을 잃지 않고 다시 시도할 수 있습니다.
- 불확실한 남은 시간을 거짓으로 표시하지 않습니다.

### 진행 결과 (2026-10-28)

- 분석 시작 전 원본, 동의, 경고 확인, 코트와 선수 설정을 다시 검사합니다.
- 중복 클릭에는 진행 중인 작업 한 건을 돌려주고 새 작업을 만들지 않습니다.
- 7단계와 처리한 영상 구간을 보여주는 개발용 작업 흐름을 만들었습니다.
- 화면을 나갔다 돌아와도 저장된 작업을 다시 조회하며 취소와 처음부터 재시도를 지원합니다.
- 15분 이상 멈춘 작업은 서버 시작 때 중단 실패로 바꾸고 재시도할 수 있게 합니다.
- 이 단계는 실제 AI 분석이 아니라고 화면과 데이터에 표시하며 가짜 슛 결과를 만들지 않습니다.

## Phase 7. 영상 분석 기초

### 목표

### 진행 작업

1. 원본 fps와 시간 정보를 유지하며 영상 프레임을 읽습니다.
2. 분석 속도를 위해 모든 프레임을 볼지 간격을 두고 볼지 기준을 정합니다.
3. 골대와 림의 위치를 찾고 프레임 사이에서 안정화합니다.
4. 개인 연습 영상의 한 선수를 찾고 발 위치를 추정합니다.
5. 농구공을 찾고 시간에 따라 이동 경로를 연결합니다.
6. 공과 선수 동작, 림 방향 이동을 조합해 슛 후보를 생성합니다.
7. 같은 슛이 여러 후보로 생기지 않도록 시간 간격을 기준으로 합칩니다.
8. 가림, 공 놓침과 화면 밖 이동 이유를 기록합니다.
9. 샘플 영상마다 후보 시간과 사람이 작성한 정답을 비교합니다.
10. 처리 진행률에 현재 분석한 영상 시간을 연결합니다.

### 테스트

- 샘플 A 초반 구간에서 슛 후보와 발 위치를 확인합니다.
- 샘플 B에서 긴 영상 처리와 중복 후보를 확인합니다.
- 골대가 없거나 공을 놓친 영상이 성공한 것처럼 완료되지 않는지 확인합니다.

### 완료 기준

- 개인 영상에서 슛 후보 시간과 선수 발 위치를 저장할 수 있습니다.
- 놓친 경우와 불확실한 경우가 이유와 함께 남습니다.
- 현재 단계의 발견률을 정답표와 비교해 기록합니다.

### 진행 결과 (2026-10-29)

- 기존 개발용 흐름 점검은 유지하고, 별도의 실제 슛 후보 분석 시작 기능을 추가했습니다.
- 로컬 학습 모델로 원본 영상의 시간과 fps를 유지하며 간격을 두고 사람·공·림을 읽습니다. 5초 실험에서 4fps는 슛을 놓치고 8fps는 후보를 찾아, 기본 분석 간격을 8fps로 정했습니다.
- 확인된 골대 위치와 림 탐지 위치가 크게 달라지는 장면은 카메라 구도가 바뀐 것으로 보고 후보 생성에서 제외합니다. 공·선수를 놓친 횟수와 불확실한 이유를 결과에 남깁니다.
- 후보 시점, 원본 프레임 번호, 선수 발의 화면 좌표와 신뢰도를 로컬 작업 폴더의 JSON에 원자적으로 저장합니다. 실제 성공·실패, 슛 종류와 코트 구역 판단은 Phase 8 범위로 남깁니다.

- 백엔드 자동 시험 46개, 프론트엔드 빌드와 정적 검사를 통과했습니다. 실제 코트 샘플의 35초 구간에서 카메라 전환으로 생긴 잘못된 후보 3개를 제거했습니다.

- Terra가 불확실할 때만 Sol이 재검토하고, 두 모델이 같은 판단을 내린 항목은 자동 확정합니다.

- 림 통과가 직접 보이지 않을 때는 화면에 보이는 공의 낙하, 리바운드 행동과 점수 표시 변화만 보조 근거로 사용하며 화면 밖 결과는 추측하지 않습니다.
- 실제 미사용 영상에서 고정 구도 4개 후보 중 3개는 결과까지 자동 확정하고 1개는 종류만 자동 확정했습니다. 다른 고정 구도 1개는 레이업 성공까지 자동 확정했고, 편집 영상 3개는 드리블 풀업을 자동 저장하고 성공 여부만 판단 불가로 남겼습니다.
- 경계 슛이 다시 검출됐으므로 이번 문제를 해결하기 위한 추가 YOLO 학습은 하지 않았습니다. 남은 불확실성은 카메라 컷으로 성공 장면 자체가 없는 경우라 탐지 학습으로 복원할 수 없습니다.
- 백엔드 전체 자동 시험 73개와 React·TypeScript 배포 빌드를 통과했습니다.

## Phase 10. 결과 화면과 2D 히트맵

### 목표

저장된 슛 기록을 이해하기 쉬운 요약과 14개 구역 히트맵으로 보여줍니다.

### 진행 작업

1. 전체 시도, 성공, 실패, 성공률과 확인 필요 수를 보여줍니다.
2. 선수별·슛 종류별 시도 수와 성공률을 보여줍니다.
3. 선수, 성공·실패와 슛 종류 결과 필터를 구현합니다.
4. 모든 결과 영역이 같은 필터 조건을 사용하게 합니다.
5. 위에서 내려다본 반코트와 14개 구역을 그립니다.
6. 구역마다 성공/시도, 성공률, 슛 비중과 전체 성공률 차이를 표시합니다.
7. 전체보다 높음은 초록, 낮음은 빨강, 비슷함은 중간색으로 표시합니다.
8. 0회는 회색과 `데이터 없음`, 1~2회는 실제 숫자와 색을 표시합니다.
9. 구역을 누르면 해당 슛 목록과 시퀀스로 연결합니다.
10. 실제 테스트 데이터를 보고 중간색으로 볼 성공률 차이 범위를 조정합니다.

### 테스트

- 14개 구역에 각각 0회, 1회, 2회와 여러 회 데이터를 넣습니다.
- 전체 평균보다 높고 낮고 같은 구역을 확인합니다.
- 필터 변경 시 요약, 히트맵과 목록이 동시에 바뀌는지 확인합니다.
- 시도 0회일 때 `기록 없음`과 0%를 혼동하지 않는지 확인합니다.

### 완료 기준

- SPEC의 14개 구역과 숫자가 정확히 표시됩니다.
- 색상 없이 숫자만 보아도 결과를 이해할 수 있습니다.
- 구역에서 실제 슛 장면까지 이동할 수 있습니다.

### 진행 기록 (2026-10-29)

- `/results/{분석번호}`에 전체 시도·성공·실패·확인 필요·성공률과 선수별·슛 종류별 통계를 추가했습니다.
- 선수, 성공 여부와 슛 종류 필터를 API와 화면에 연결해 요약, 14개 구역 히트맵과 슛 목록이 같은 조건을 사용하도록 했습니다.
- 참고 이미지처럼 나무색 반코트, 검은 구역 경계, 흰 코트 선과 구역별 반투명 수치 카드를 사용했습니다. 각 카드에는 성공/시도, 성공률, 현재 필터 전체 평균과 슛 비중을 표시합니다.
- 전체 평균보다 높음은 초록, 낮음은 빨강, 비슷함은 노랑, 기록 없음은 회색으로 구분하고 색상 없이도 숫자로 결과를 읽을 수 있게 했습니다.
- 구역을 누르면 해당 구역의 슛 목록으로 좁혀지고, 슛을 선택하면 저장된 원본 장면으로 연결됩니다.
- `fOXMTSF7oug`의 실제 40초 구간을 등록부터 YOLO·OpenAI·Supabase 저장까지 실행해 슛 3건과 결과 통계를 웹 결과 API에서 확인했습니다.
- 시험 영상의 `FMP4/mp4v`가 Chrome에서 재생되지 않는 문제를 확인해, 비호환 MP4는 원본을 보존하면서 H.264 재생 사본을 자동 생성하도록 보완했습니다.
- 백엔드 전체 자동 시험 75개와 React·TypeScript 배포 빌드를 통과했고, 실제 H.264 영상에 Range 요청이 206으로 응답하는 것을 확인했습니다.
- 실제 화면에서 좌우 미드레인지와 3점 구역 사이가 비고 상단 통계 카드가 겹치는 문제를 확인해, 14개 구역의 공유 경계를 다시 연결하고 코너·페인트존 카드 크기와 위치를 조정했습니다.
- 사용자 점검에서 좌우 코너가 작고 외곽선이 잘리는 문제를 확인해, 히트맵을 결과 카드 전체 폭으로 확대하고 코트 둘레에 안전 여백을 추가했습니다. 선수별·슛 종류별 통계는 히트맵 아래에 배치했습니다.
- 확대 후에도 코너 카드의 긴 수치가 잘리는 것을 확인해 양쪽 카드 폭과 위치를 조정했습니다. 코트 선은 수치 카드 뒤에 표시되도록 그리기 순서를 바꿔 중앙 숫자가 가려지지 않게 했습니다.
- 미드레인지 통계 카드 3개가 아래쪽 3점 경계선을 넘어가던 문제를 확인해 각 회색 구역 안쪽으로 올려 배치했습니다.
- 따라서 **Phase 10을 완료**하고 다음 작업은 Phase 11의 3D 슈팅 맵입니다.

### 목표

반코트 위에서 각 슛 위치와 성공·실패를 입체적으로 살펴볼 수 있게 합니다.

### 진행 작업

6. 선택한 슛의 전체 시퀀스 재생으로 연결합니다.
7. 같은 위치의 여러 슛은 약간 나누거나 묶음 수로 표시합니다.

- 회전·확대 후 초기 시점으로 정확히 돌아가는지 확인합니다.

- 2D 히트맵과 3D 맵이 같은 필터와 데이터를 사용합니다.

## Phase 12. 기록 보관·삭제·실패 복구

### 목표

프로그램을 다시 켜도 분석 결과가 남고, 사용자가 원본과 결과를 안전하게 관리할 수 있게 합니다.

### 진행 작업

1. 시작 화면에 최근 등록 순서로 분석 기록을 표시합니다.
2. 상태에 따라 결과 화면, 진행 화면 또는 설정 화면으로 이동합니다.
3. 검색과 과거 목록 필터는 넣지 않습니다.
4. 프로그램과 PC를 다시 시작해도 원본, 설정, 슛과 수정 결과를 복구합니다.
5. 원본이 없어졌거나 저장 정보가 깨진 기록을 정상 완료처럼 보이지 않게 합니다.
6. 삭제 확인 창에 분석 이름과 삭제 범위를 보여줍니다.
7. 확인 후 원본, 코트, 선수, 슛과 통계를 함께 삭제합니다.
8. 일부 삭제 실패 시 남은 항목과 재시도 방법을 표시합니다.
9. 분석 불가, 일부 확인 필요와 외부 AI 실패를 서로 다른 상태로 보여줍니다.
10. 다시 분석 전에 기존 중간 결과를 안전하게 정리합니다.

### 테스트

- 프로그램과 PC 재시작 후 결과와 장면 재생을 확인합니다.
- 삭제 취소와 실제 삭제를 각각 시험합니다.
- 영상 파일만 수동으로 없앤 상태와 데이터만 손상된 상태를 시험합니다.
- 삭제 도중 실패를 만들어 전부 삭제된 것처럼 표시하지 않는지 확인합니다.

### 완료 기준

- 재실행 후 이전 작업을 계속 사용할 수 있습니다.
- 삭제 대상과 결과가 분명하며 부분 실패를 숨기지 않습니다.
- 깨진 기록이 정상 결과로 표시되지 않습니다.

최대 6명의 선수를 등록하고 각 슛의 슈터를 연결·수정하여 선수별 결과를 볼 수 있게 합니다.

### 진행 작업

4. 가림 뒤 추적이 바뀔 가능성이 있으면 확정하지 않고 표시합니다.
5. 슛 후보와 가장 가능성 높은 슈터를 연결합니다.

8. 자동 구분이 실패해도 수동 지정으로 결과를 완성할 수 있게 합니다.

### 테스트

- 수동으로 각 선수에게 슛을 배정해 선수별 통계를 검증합니다.
- 두 선수가 겹치거나 화면 밖으로 나갔다 돌아오는 장면을 시험합니다.
- 자동 추적 정확도와 실패 유형은 별도 참고 결과로 기록합니다.

### 완료 기준

- 3대3의 등록, 화면 지정, 슈터 저장·수정과 선수별 결과 흐름이 동작합니다.
- 자동 추적이 틀려도 사용자가 결과를 바로잡을 수 있습니다.
- 3대3 자동 정확도는 개인 영상 MVP 합격 조건과 분리되어 있습니다.

## Phase 14. 정확도·성능·발표 준비

### 목표

### 진행 작업

- 개인 연습 슛 발견률: 실제 슛의 80% 이상
- 발견한 슛의 성공·실패 판단: 85% 이상
- 프로그램 재실행 후 저장 결과 유지
- 확인 필요 기록을 사용자가 수정해 최종 결과 완성 가능

### 최종 완료 기준

- 정상 개인 연습 영상이 등록부터 결과 확인까지 끝까지 처리됩니다.

- 사용자가 틀린 분석을 추가·수정·삭제할 수 있습니다.
- 취소, 실패, 다시 시도, 재실행과 삭제가 안전하게 동작합니다.
- 실제 정확도와 처리 시간이 문서에 기록되어 있습니다.
- 발표 방식이 현재 PC의 실제 성능을 바탕으로 결정되어 있습니다.

## 4. Phase 사이의 핵심 의존 관계

```text
기술·시험 준비
  → 저장과 데이터 구조
    → 영상 등록
      → 코트·선수 설정
        → 분석 작업 흐름
          → 슛 후보 감지
            → 결과·종류 판단
              → 검토와 수정
                → 2D·3D 결과 화면
                  → 3대3 확장
                    → 정확도·발표 검증
```

영상 분석 정확도가 늦게 개선되더라도 저장, 수동 수정, 히트맵과 3D 화면 개발은 예시 데이터로 먼저 진행할 수 있습니다. 다만 최종 통합은 실제 분석 결과가 저장되는 Phase 8 이후에 진행합니다.

## 5. 개발 중 중간 판단 지점

### Phase 7 종료 후

- 현재 PC에서 슛 후보 감지가 가능한 속도인지 판단합니다.
- 너무 느리면 프레임 간격, 영상 해상도와 분석 구간을 조정합니다.
- 개인 영상에서도 발견률이 매우 낮으면 3대3 자동 추적보다 개인 분석을 우선 개선합니다.

### Phase 8 종료 후

- OpenAI가 실제로 도움이 되는 항목과 로컬 분석만으로 충분한 항목을 구분합니다.
- 스텝백, 턴어라운드와 훅슛을 자동 종류로 유지할지 판단합니다.
- 비용과 정확도를 함께 기록하고 불필요한 호출을 줄입니다.

### Phase 13 종료 후

- 현재 PC에서 3대3 자동 추적이 발표에 사용할 수준인지 판단합니다.
- 부족하면 수동 선수 지정과 슈터 수정 흐름을 중심으로 시연합니다.

### Phase 14 종료 후

- 발표 때 현장 분석을 할지 미리 분석한 결과를 사용할지 결정합니다.
- 현재 PC가 부족할 때만 클라우드 GPU의 필요성과 비용을 별도로 검토합니다.

## 6. 사용자가 준비할 항목

### 개발 시작 전에 필요한 것

- OpenAI API 키: 실제 값은 환경설정 파일에 사용자가 직접 입력
- 샘플 영상 사용 구간의 사람이 확인한 정답 기록
- 직접 촬영 가능한 농구 코트와 고정 촬영 장비 또는 삼각대
- 최소 1분짜리 최종 검증용 개인 연습 영상

### 개발 후반에 필요한 것

- 가능하면 1080p 60fps로 촬영한 최대 10분 개인 영상
- 성공과 실패, 여러 슛 위치, 제자리·풀업·레이업이 섞인 영상
- 3대3 화면 흐름을 확인할 수 있는 짧은 영상 또는 촬영 협조자

OpenAI API 키 외의 비밀값은 문서나 Git에 기록하지 않습니다.
