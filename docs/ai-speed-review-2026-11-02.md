## 3. 실제 Terra API 속도 비교

기존 실내 영상의 1.600초 레이업과 14.933초 제자리 슛을 사용했다. 두 장면은 앞선 사람·화면 확인에서 성공으로 기록된 시험용 사례다. 독립적인 대규모 정답 자료는 아니다.

- 기존 모델 `gpt-6.1-terra`, reasoning `low`, 프롬프트·스키마·22장 이미지 모두 유지했다. 입력 이미지의 SHA-256을 저장했다.
- 같은 공통 카메라 해석과 저장된 발 투영값을 재사용했다. **실제 API 시험은 기본 상세 판정 함수 비교**다. 전체 파이프라인의 카메라 재판정·조건별 추가 호출·DB 저장까지 실제로 비교한 것은 아니다.
- 순차 2개와 동시에 2개를 비교했다. 먼저 순차→병렬 4회, 이어 캐시가 준비된 상태에서 순서를 바꿔 병렬→순차 4회로 확인했다. 총 추가 유료 요청 **8회**, 실패·자동 재시도 0회다. 솔·아스트라는 호출하지 않았다.

| 비교 | 순차 | 동시 2개 | 관찰된 감소 |
|---|---:|---:|---:|
| 첫 시험: 순차는 캐시 없음, 병렬은 캐시 적용 | 16.6553초 | 7.3545초 | 약 55.8% |
| 두 번째: 양쪽 모두 캐시 적용, 순서 반대 | 13.3315초 | 8.3702초 | 약 37.2% |

두 번째 시험은 모든 요청에서 입력 23,001토큰 중 22,998토큰이 캐시로 보고됐다. 첫 시험은 캐시 조건이 달라 병렬만의 개선율로 해석하지 않는다. 두 번째도 요청별 출력 길이·응답 시간 변동이 있으며 두 슛뿐이므로 전체 분석의 고정 개선율로 보장하지 않는다.

모든 호출에서 레이업/제자리 슛, 성공, 왼쪽 페인트존/정면 미드레인지, 확인 필요 아님이 일치했다. 숫자 좌표·설명·신뢰도까지 완전히 같은 응답이라는 뜻은 아니다. 이번 실험은 **기본 판단 8회 입력 184,008·출력 2,427토큰**을 사용했으며 기존 10분 작업 사용량과 별도다. 동시 처리는 원칙적으로 호출 개수를 줄이는 방법이 아니다.

## 4. 실험 코드와 검증

- `backend/app/services/openai_shot_review.py` 실험본에 후보 동시 처리 옵션 `detail_workers=1 또는 2`와 이미지 준비·기본 판단·위치·득점 재검토 시간을 기록하는 계측을 추가했다.
- 공통 카메라 해석을 먼저 끝낸다. 후보 안의 기본 판단→조건별 재검토 순서는 유지한다. 두 후보만 동시에 진행하고, 입력 순서로 결과를 모은 뒤 장면 전체 일관성 검사와 사용량 집계를 수행한다.
- 슛 여부 판정·릴리스 시각 보정·중복 검사 경로는 병렬화하지 않았다. 이 경로는 앞 후보의 변경과 호출 한도에 의존한다.
- 전체 자동 시험 **153개 통과**. 순차·병렬에서 득점 추가 판정과 위치 충돌 재검토의 결정·사용량·순서가 같고 최대 두 작업만 실행되는 시험을 포함한다. API를 흉내 낸 자동 시험과 위 실제 API 시험을 구분한다.
- 실행 스크립트: `backend/evaluation/live_detail_speed_trial.py`. 실행하면 과금되므로 자동 재실행하지 않는다. 한 번 실행당 4회로 제한하고 SDK 재시도는 끈 상태다.
- 상세 원본 측정은 실험본 `backend/work/speed-lab/live-detail.json`, `live-detail-warm.json`, `long-video-image-preparation.json`에 있다. 비밀값·이미지 본문·환경설정 값은 출력하거나 보고서에 저장하지 않았다.

## 5. 다음 적용 우선순위

1. **화면 단계를 세분화하고 내부 처리 개수·개별 시간·호출 실패 종류를 계측**한다. 슛 여부 확인/집중 재탐지/상세 판정/재검토를 분리해 정체와 정상 대기를 구분한다. 예외 원문 대신 안전한 오류 종류·상태 코드만 남긴다.
2. **상세 판단 후보 두 개 동시 처리**를 적용 후보로 삼는다. 모델과 입력은 유지하고 API 제한·재시도 횟수·전체 사용량을 함께 확인한다. 실제 실패·불명확 득점·위치 재검토 사례를 포함한 소규모 전체 파이프라인 시험을 먼저 한다.
3. **다음 후보 이미지 준비를 API 대기와 겹친다.** 후보 두 개의 준비·호출 전체를 묶어 동시에 실행하면 현재 두 작업 옵션에서 함께 겹칠 수 있다. 무제한 영상 캡처·이미지 보관은 피한다.
4. **DB 상태 접근을 탐지 루프 밖으로 분리**한다. 이미 별도 실험에서 시험했지만 실제 Supabase의 읽기·저장·취소 반응 확인 후 채택한다.
5. **완료된 동일 입력 판정의 재사용·중간 결과 저장**을 검토한다. 영상·모델·프롬프트·기준점·후보 시각이 다르면 재사용하지 않는다. 단순히 비슷한 장면이라는 이유로 공유하지 않는다.

정확도 유지가 목표이므로 먼저 프레임을 줄이거나 작은 모델로 바꾸거나 재검토를 없애지 않는다. 속도 개선은 후보 수·릴리스·득점·종류·구역·확인 필요 비율을 함께 비교한다. 현재 서버에는 이 실험본을 반영하지 않았다.

공식 근거: [OpenAI Docs: Latency optimization](https://developers.openai.com/api/docs/guides/latency-optimization). 독립 요청 병렬화는 지연을 줄이는 접근이지만 결과 품질과 제한을 실제 자료로 검증해야 한다.
